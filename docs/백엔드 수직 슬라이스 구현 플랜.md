# 백엔드 수직 슬라이스 구현 플랜

> 구현 결과 문서 · 최종 갱신 2026-07-28: 계획한 백엔드 소스는 구현됐다. 컴파일과 추천 알고리즘 단위 테스트는 통과했으며, 실제 Oracle 기반 전체 컨텍스트와 Flyway V20~V22 검증은 로컬 DB 인증 문제로 남아 있다. 이 문서의 코드 블록은 구현 의도를 설명하는 설계 예시이며 정확한 외부 계약은 API 명세, 스키마는 DB 설계, 실행 동작은 현재 소스를 우선한다.

## 1. 문서 목적

이 문서는 테스트에서 발견된 결과 화면 문제와 다음 신규 기능을 백엔드에서 구현하기 위한 실행 계획이다.

- 방장만 모임 확정
- 확정 결과를 `resultToken` 공개 링크로 조회
- 공개 결과 링크에서 참여자 이름과 개인별 가능 시간까지 조회
- 30분 블록을 분석해 사람이 가장 많이 겹치는 연속 시간 구간을 만들고 정렬별 상위 6개 조회
- 카카오 닉네임과 별개인 서비스 전용 닉네임 조회·수정
- 내가 만들거나 카카오 계정으로 참여한 모임 조회
- 방장이 `OPEN` 모임의 참여자를 soft delete
- CandidateSlot을 날짜별 하나의 결과 카드로 생성
- 확정된 모임에서 시간 재선택 방지

구현은 화면 단위 수직 슬라이스로 진행한다. 한 슬라이스 안에서 DB, Entity, Repository, Service, Controller, DTO, 보안, 테스트를 함께 완성한 뒤 다음 슬라이스로 넘어간다.

## 2. 확정된 정책

### 2.1 결과 공개 범위

- `InviteResultPage`는 `inviteToken`으로 조회한다.
- `ResultSharePage`는 `resultToken`으로 조회한다.
- `resultToken` 링크는 공개 링크다.
- 기획상 공개 결과 링크에서도 참여자 이름과 개인별 가능 시간을 노출해도 된다.
- 공개 링크이므로 응답에는 PIN, 카카오 ID, 내부 User ID 등 인증정보를 절대 포함하지 않는다.

### 2.2 서비스 닉네임

- 카카오 닉네임과 서비스에서 사용할 닉네임을 분리한다.
- 사용자가 서비스 닉네임을 설정하면 서비스 닉네임을 우선 사용한다.
- 서비스 닉네임이 없으면 카카오 닉네임을 사용한다.
- 카카오 재로그인 시 카카오 닉네임만 갱신하고 서비스 닉네임은 덮어쓰지 않는다.
- 이미 참여한 모임의 `Participant.displayName`은 참여 당시 스냅샷으로 유지한다.

### 2.3 참여자 삭제

- 방장만 삭제할 수 있다.
- `OPEN` 상태에서만 삭제할 수 있다.
- `CONFIRMED`, `EXPIRED` 상태에서는 삭제할 수 없다.
- 방장 자신은 삭제할 수 없다.
- Participant, Availability, AvailabilityTimeRange는 soft delete한다.
- 삭제된 참여자의 응답은 결과 집계에서 제외한다.

### 2.4 공통 시간 추천과 확정

- 결과 카드 하나는 CandidateSlot 전체가 아니라 CandidateSlot 안에서 사람들이 실제로 겹치는 연속 시간 구간 하나를 뜻한다.
- CandidateSlot은 날짜와 탐색 가능한 전체 시간 범위를 제공하는 부모 단위로 유지한다.
- CandidateSlot을 30분 블록으로 나눈 뒤 각 블록에서 가능한 참여자 집합을 구한다.
- 인접한 블록의 가능한 참여자 집합이 같으면 하나의 연속 구간으로 병합한다.
- 가능한 참여자가 0명인 구간은 추천 카드에서 제외한다.
- 추천순은 `가능 인원 내림차순 → 구간 길이 내림차순 → 날짜 오름차순 → 시작 시간 오름차순`이다.
- 추천 화면은 정렬된 공통 시간 구간을 한 번에 6개씩 반환한다.
- 방장은 CandidateSlot 전체가 아니라 추천 카드의 `candidateSlotId + startTime + endTime`을 확정한다.
- 서버는 확정 요청 시 해당 구간을 다시 계산하여 조작된 시간 범위를 거부한다.

## 3. 구현 전 기준선에서 발견했던 문제

1. `MeetingService.confirm()`이 `resultToken` 없는 `MeetingDetailResponse`를 반환한다.
2. 확정 요청의 CandidateSlot이 대상 Meeting 소속인지 검사하지 않는다.
3. 초대 토큰 조회가 Authentication을 받지 않아 `isOwner`가 항상 false다.
4. `AvailabilityService`가 `CONFIRMED` 상태에서도 시간 수정과 제출을 허용한다.
5. `ResultService`는 CandidateSlot 단위 집계만 제공하며 참여자별 상세 응답은 없다.
6. `resultToken` 조회는 확정 슬롯만 제공하고 히트맵과 개인별 시간은 제공하지 않는다.
7. `User.name`을 카카오 로그인마다 갱신하므로 서비스 전용 닉네임을 보존할 수 없다.
8. `MyMeetingResponse`와 Repository 메서드만 있고 `/api/my/**` 구현이 없다.
9. V19는 기존 모임의 방장을 LEADER로 보강하지만, V19 실행 이후 생성하는 새 모임에는 방장 Participant가 자동 생성되지 않는다.
10. Participant soft delete 후 Availability를 직접 조회하면 삭제된 참여자의 응답이 집계에 남을 수 있다.
11. 하나의 CandidateSlot이 여러 날짜 범위를 가지므로 “하루에 카드 하나”라는 화면 모델과 맞지 않는다.
12. CORS 허용 메서드에 `PATCH`, `DELETE`가 없다.
13. API 응답에서 `Map<String, Object>` 사용이 많아 프런트 계약과 테스트가 불안정하다.
14. 현재 결과 정렬은 CandidateSlot 전체의 AVAILABLE 응답 수를 사용하므로, 실제로 사람이 많이 겹치는 부분 시간대를 별도 추천 카드로 만들지 못한다.
15. Meeting에는 `confirmed_slot_id`만 있어 CandidateSlot 내부의 일부 시간 구간을 확정해 저장할 수 없다.

# 슬라이스 1. 날짜별 CandidateSlot 생성과 방장 자동 참가

## 목표

- 날짜 범위 하나를 날짜별 CandidateSlot 여러 개로 정규화한다.
- 새 모임 생성 시 방장을 LEADER Participant로 함께 저장한다.
- CandidateSlot 하나는 날짜 하나의 탐색 범위가 되며, 그 안에서 여러 공통 시간 추천 카드가 파생될 수 있게 한다.

## 변경 파일

- `MeetingService`
- `CandidateSlotRepository`
- 필요 시 기존 다일 슬롯 정리용 Flyway migration

## Repository 추가

```java
public interface CandidateSlotRepository extends JpaRepository<CandidateSlot, Long> {

    Optional<CandidateSlot> findByIdAndMeeting(Long id, Meeting meeting);
}
```

## MeetingService의 create 전체 교체 대상 메서드

```java
public MeetingCreateResponse create(Long userId, MeetingCreateRequest request) {
    User user = userRepository.findById(userId)
            .orElseThrow(() -> new CustomException(ErrorCode.UNAUTHORIZED));

    Meeting meeting = meetingRepository.save(Meeting.builder()
            .owner(user)
            .name(request.getName())
            .expectedCount(request.getExpectedCount())
            .inviteToken(UUID.randomUUID().toString())
            .resultToken(UUID.randomUUID().toString())
            .build());

    participantRepository.save(Participant.builder()
            .meeting(meeting)
            .user(user)
            .displayName(user.getDisplayName())
            .type(ParticipantType.LEADER)
            .build());

    request.getCandidateSlots().forEach(requestSlot -> {
        LocalDate date = requestSlot.getStartDate();
        while (!date.isAfter(requestSlot.getEndDate())) {
            candidateSlotRepository.save(CandidateSlot.builder()
                    .meeting(meeting)
                    .startDate(date)
                    .endDate(date)
                    .startTime(requestSlot.getStartTime())
                    .endTime(requestSlot.getEndTime())
                    .build());
            date = date.plusDays(1);
        }
    });

    return new MeetingCreateResponse(meeting, FRONT_BASE_URL);
}
```

`MeetingService`에 `ParticipantRepository` 의존성을 추가한다.

## 기존 데이터 처리

개발 DB를 초기화할 수 있으면 초기화가 가장 안전하다. 운영 데이터가 있다면 다일 CandidateSlot을 단순 분할하면 기존 Availability와 확정 FK를 재연결해야 하므로 Java 기반 Flyway migration 또는 별도 데이터 이관 작업으로 처리한다.

## 완료 조건

- 7월 1일~3일 요청이 CandidateSlot 3건으로 저장된다.
- 각 슬롯의 `startDate == endDate`다.
- 방장이 별도 참여 요청 없이 LEADER Participant로 존재한다.
- 정원과 참여자 수에 방장이 포함된다.

# 슬라이스 2. 공통 시간 추천 조회와 모임 확정

## 목표

- CandidateSlot 전체가 아니라 사람이 실제로 많이 겹치는 연속 시간 구간을 결과 카드로 만든다.
- 추천/날짜/긴 시간 정렬별로 공통 시간 구간을 한 번에 6개 반환한다.
- 요청자가 방장인지 응답한다.
- 방장만 추천 구간을 확정할 수 있다.
- 확정한 CandidateSlot과 실제 시작·종료 시간을 함께 저장한다.
- 확정 응답에 `resultToken`을 포함한다.
- 확정된 모임의 시간 변경을 차단한다.

## DB migration

파일: `V20__add_confirmed_time_range.sql`

```sql
ALTER TABLE meetings ADD (
    confirmed_start_time TIMESTAMP,
    confirmed_end_time   TIMESTAMP
);

ALTER TABLE meetings ADD CONSTRAINT chk_meeting_confirmed_range
CHECK (
    (confirmed_slot_id IS NULL
        AND confirmed_start_time IS NULL
        AND confirmed_end_time IS NULL)
    OR
    (confirmed_slot_id IS NOT NULL
        AND confirmed_start_time IS NOT NULL
        AND confirmed_end_time IS NOT NULL
        AND confirmed_start_time < confirmed_end_time)
);
```

Oracle JDBC와 기존 엔티티가 `LocalTime`을 사용하므로 실제 컬럼 타입은 개발 Oracle에서 매핑을 검증한다. 날짜별 CandidateSlot이므로 단순 TIME 타입이 없는 Oracle에서는 `TIMESTAMP`에 기준 날짜를 결합하거나, `NUMBER(4)` 분 단위 컬럼을 사용하는 대안도 가능하다. 프로젝트 전체에서 일관되게 사용할 수 있도록 최종 선택을 ERD에 반영한다.

```java
private record Block(
        LocalTime startTime,
        LocalTime endTime,
        Set<Long> participantIds

private record RecommendedWindow(

        LocalTime startTime,
```

## 추천 구간 산출 알고리즘

CandidateSlot마다 다음 순서로 계산한다.

1. 슬롯 시작부터 종료까지 30분 블록을 생성한다.
2. 각 블록 전체를 덮는 `AVAILABLE` 참여자의 ID 집합을 구한다.
3. `participantIds`가 빈 블록은 추천 후보에서 제외하고 진행 중인 구간을 종료한다.
4. 직전 블록과 현재 블록이 인접하고 `participantIds` 집합이 완전히 같으면 하나의 구간으로 병합한다.
5. 참여자 집합이 달라지면 직전 구간을 완료하고 새 구간을 시작한다.
6. 모든 CandidateSlot에서 만들어진 `RecommendedWindow`를 하나의 목록으로 합친다.
7. 중복 구간이 생기지 않도록 `(candidateSlotId, startTime, endTime)` 기준으로 제거한다.
8. 요청한 정렬을 적용한 다음 페이지 크기 6으로 자른다.

핵심 병합 코드:

```java
private List<RecommendedWindow> mergeBlocks(
        CandidateSlot slot,
        List<Block> blocks
) {
    List<RecommendedWindow> windows = new ArrayList<>();
    LocalTime windowStart = null;
    LocalTime windowEnd = null;
    Set<Long> currentParticipants = Set.of();
    List<Block> currentBlocks = new ArrayList<>();

    for (Block block : blocks) {
        if (block.participantIds().isEmpty()) {
            addWindow(windows, slot, windowStart, windowEnd,
                    currentParticipants, currentBlocks);
            windowStart = null;
            windowEnd = null;
            currentParticipants = Set.of();
            currentBlocks = new ArrayList<>();
            continue;
        }

        boolean mergeable = windowStart != null
                && windowEnd.equals(block.startTime())
                && currentParticipants.equals(block.participantIds());

        if (!mergeable) {
            addWindow(windows, slot, windowStart, windowEnd,
                    currentParticipants, currentBlocks);
            windowStart = block.startTime();
            currentParticipants = Set.copyOf(block.participantIds());
            currentBlocks = new ArrayList<>();
        }

        windowEnd = block.endTime();
        currentBlocks.add(block);
    }

    addWindow(windows, slot, windowStart, windowEnd,
            currentParticipants, currentBlocks);
    return windows;
}

private void addWindow(
        List<RecommendedWindow> windows,
        CandidateSlot slot,
        LocalTime start,
        LocalTime end,
        Set<Long> participants,
        List<Block> blocks
) {
    if (start == null || end == null || participants.isEmpty()) {
        return;
    }
    windows.add(new RecommendedWindow(
            slot, start, end, Set.copyOf(participants), List.copyOf(blocks)));
}
```

예:

```text
13:00~13:30: 철수, 영희, 민수
13:30~14:00: 철수, 영희, 민수
14:00~14:30: 철수, 영희
14:30~15:00: 철수, 영희
```

추천 카드는 다음 두 개가 된다.


## 정렬 규칙

```java
private Comparator<RecommendedWindow> comparator(String sort) {
    Comparator<RecommendedWindow> byCount =
            Comparator.comparingInt(RecommendedWindow::availableCount).reversed();
    Comparator<RecommendedWindow> byDuration =
            Comparator.comparingInt(RecommendedWindow::durationMinutes).reversed();
    Comparator<RecommendedWindow> byDate =
            Comparator.comparing(w -> w.slot().getStartDate());
    Comparator<RecommendedWindow> byStart =
            Comparator.comparing(RecommendedWindow::startTime);

    return switch (sort) {
        case "date" -> byDate.thenComparing(byStart)
                .thenComparing(byCount).thenComparing(byDuration);
        case "duration" -> byDuration.thenComparing(byCount)
                .thenComparing(byDate).thenComparing(byStart);
        default -> byCount.thenComparing(byDuration)
                .thenComparing(byDate).thenComparing(byStart);
    };
}
```

`recommend`일 때 사람이 많이 겹치는 구간이 우선이며, 같은 인원수라면 더 긴 구간이 먼저다. `date`, `duration` 탭에서도 CandidateSlot 전체가 아니라 위 알고리즘으로 만들어진 공통 시간 구간을 정렬한다.

```java
@Transactional
public void remove(Long meetingId, Long participantId, Long requesterId) {
    Meeting meeting = meetingRepository.findByIdForUpdate(meetingId)
            .orElseThrow(() -> new CustomException(ErrorCode.MEETING_NOT_FOUND));

    if (!meeting.getOwner().getId().equals(requesterId)) {
        throw new CustomException(ErrorCode.FORBIDDEN);
    }
    if (meeting.getStatus() != MeetingStatus.OPEN) {
        throw new CustomException(ErrorCode.PARTICIPANT_DELETE_NOT_ALLOWED);
    }

    Participant participant = participantRepository
            .findByIdAndMeeting(participantId, meeting)
            .orElseThrow(() -> new CustomException(ErrorCode.PARTICIPANT_NOT_FOUND));

    if (participant.getType() == ParticipantType.LEADER
            || participant.getUser() != null
            && participant.getUser().getId().equals(requesterId)) {
        throw new CustomException(ErrorCode.CANNOT_DELETE_LEADER);
    }

    availabilityRepository.findByParticipant(participant)
            .forEach(Availability::softDeleteWithRanges);
    participant.delete();
}
```

```java
        Authentication authentication) {
    participantService.removeByInviteToken(
            inviteToken,
            participantId,
            memberId(authentication));
    return ResponseEntity.noContent().build();
}
```

## 재참가 정책

soft delete된 회원 Participant가 다시 참가하면 Oracle의 기존 unique index와 충돌할 수 있다. 다음 중 하나를 구현해야 한다.

1. 삭제된 Participant를 native query로 찾아 `deleted_at = null`로 복구하고 기존 Availability는 초기화
2. unique index에 `deleted_at` 조건을 반영해 새 Participant 생성 허용

Oracle에서는 조건부 unique index 관리가 복잡하므로 1번 복구 방식을 권장한다. 단, `@SQLRestriction` 때문에 JPA 일반 조회로 삭제 행을 읽을 수 없으므로 native query 전용 Repository를 둔다.

## DTO 원칙

- 신규 API에서는 `Map<String, Object>`를 사용하지 않는다.
- Entity를 직접 JSON으로 반환하지 않는다.
- 날짜는 `LocalDate`, 시간은 `LocalTime`, 생성 시각은 `LocalDateTime`으로 통일한다.
- `isOwner`의 JSON 이름은 프런트 타입과 맞춘다.
- 공개 응답에서 `pinHash`, `kakaoId`, `userId`를 제외한다.

## 트랜잭션 원칙

- 조회 Service: `@Transactional(readOnly = true)`
- 확정, 참여자 삭제, 닉네임 수정: `@Transactional`
- 정원 확인, 확정, 참여자 삭제: Meeting 비관적 잠금
