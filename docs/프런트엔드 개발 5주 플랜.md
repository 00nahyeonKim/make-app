## 2. 기본 개발 원칙

### 2.1 구현 원칙

- 처음부터 완벽한 코드를 만들기보다, 화면 흐름을 먼저 연결한다.
- API가 아직 없으면 목데이터를 사용하고, API가 완성되면 `api/` 함수만 교체한다.
- 페이지 컴포넌트에 `fetch`를 직접 작성하지 않는다.
- 반복되는 UI는 공통 컴포넌트로 분리한다.
- 모바일 화면을 우선으로 만들고, 필요한 경우 PC 대응을 추가한다.
- 단일 화면에서만 쓰는 상태는 `useState`를 사용한다.
- 로그인 정보, 게스트 토큰, 모임 생성 임시값처럼 여러 화면에서 공유하는 상태는 Zustand를 사용한다.

### 2.2 학습 원칙

- 하루에 새 개념을 너무 많이 넣지 않는다.
- 매일 작은 화면이나 파일 하나를 완성하는 것을 목표로 한다.
- 개념 학습 후 바로 프로젝트 코드에 적용한다.
- 에러가 나면 에러 메시지, 원인, 해결 방법을 `troubleshooting.md`에 정리한다.
- React 문법을 외우기보다 화면이 다시 렌더링되는 흐름을 이해한다.

# 2주차: 인증 흐름 + Zustand 토큰 관리

## 목표

리더가 최종 일정을 확정, 마감, 취소할 수 있고, 내가 만든 모임 목록을 확인할 수 있으며, 전체 사용자 흐름을 실제 백엔드와 연결해 검증한다.

## 백엔드와의 연결

백엔드는 5주차에 모임 확정, 마감, 취소, 내 모임 목록, CORS 설정, 전체 E2E 테스트를 진행한다. 프런트는 이 시점에 모든 API 연동을 점검하고 사용자 경험을 정리한다.

## 5주차 일자별 계획

| 일차 | 기능                  | 학습 포인트                                                      | 작업                                                                   | 완료 기준                              |
| ---- | --------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------- | -------------------------------------- |
| 1일  | 모임 관리 화면        | 리더 화면과 팔로워 화면 분리, 권한에 따른 버튼 표시, 상태값 분기 | `MeetingManagePage.tsx` 작성, 참여자 현황과 결과 요약 표시             | 리더 관리 화면에서 현재 상태 확인 가능 |
| 2일  | 확정, 마감, 취소 API  | POST 액션 API, 확인 모달, 403/409 에러 처리                      | `confirmMeeting`, `expireMeeting`, `cancelMeeting` 연결                | 일정 확정, 마감, 취소 버튼 동작        |
| 3일  | 마이페이지            | 리스트 렌더링, 상태 필터, 페이지네이션, 빈 상태 UI               | `MyMeetingsPage.tsx`, `myApi.ts` 작성                                  | 내가 만든 모임 목록 조회 가능          |
| 4일  | 실제 백엔드 통합 점검 | CORS, 환경변수, API baseURL, 공통 에러 UI                        | 실제 백엔드 주소 연결, 401/403/404/409/410 에러 화면 점검              | 주요 API가 실제 서버와 정상 통신       |
| 5일  | 전체 E2E 테스트       | 사용자 시나리오 테스트, 디버깅 기록, 리팩토링 기준               | 로그인 → 모임 생성 → 초대 접속 → 참여 → 응답 → 결과 → 확정 전체 테스트 | 서비스 핵심 흐름 전체 통과             |

# 9. 주의할 점

- 1주차에는 API 연동에 집착하지 말고 화면 구조를 먼저 완성한다.
- 2주차 인증은 어렵기 때문에 로그인 성공 흐름, 토큰 저장, 보호 라우트만 먼저 완성한다.
- 3주차부터는 백엔드 API 응답 형태가 바뀔 수 있으므로 타입 파일을 자주 점검한다.
- 4주차 가능 시간 선택 화면은 상태 관리가 복잡해질 수 있으므로 작은 컴포넌트로 나누어도 된다.
- 5주차에는 새 기능 추가보다 통합 테스트와 에러 처리에 집중한다.
- 막히는 부분은 코드만 수정하지 말고 원인과 해결 과정을 기록한다.
