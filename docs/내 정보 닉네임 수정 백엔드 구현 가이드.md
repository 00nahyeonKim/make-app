# 내 정보 닉네임 수정 백엔드 구현 가이드

## 1. 목표

카카오 로그인 회원이 카카오에서 받은 닉네임과 별개로 이 서비스에서 사용할 닉네임을 설정할 수 있게 한다.

구현할 API는 다음 두 가지다.

| 기능 | Method | URL |
|---|---|---|
| 내 정보 조회 | GET | `/api/my/profile` |
| 서비스 닉네임 수정 | PATCH | `/api/my/profile` |

닉네임 표시 규칙은 다음과 같다.

1. 사용자가 서비스 닉네임을 설정했다면 서비스 닉네임을 표시한다.
2. 서비스 닉네임이 없다면 카카오 닉네임을 표시한다.
3. 카카오에 다시 로그인해도 서비스 닉네임은 덮어쓰지 않는다.
4. 카카오 닉네임이 바뀌었다면 카카오 닉네임만 최신 값으로 갱신한다.

예를 들어 카카오 닉네임이 `홍길동`이고 서비스 닉네임을 `회의왕`으로 설정했다면 화면에는 `회의왕`을 보여준다. 아직 서비스 닉네임을 설정하지 않은 회원에게는 `홍길동`을 보여준다.

---

## 2. 현재 코드의 문제점

현재 `User` 엔티티에는 다음 필드 하나만 있다.

```java
@Column(nullable = false, length = 50)
private String name;
```

그리고 카카오 로그인 때마다 다음 코드가 실행된다.

```java
user.updateName(name);
```

따라서 `name`을 서비스 닉네임으로 재사용하면 다음 로그인 때 카카오 닉네임으로 덮어써진다. 하나의 컬럼이 아래 두 가지 의미를 동시에 담당하기 때문에 생기는 문제다.

- 카카오가 제공한 최신 닉네임
- 사용자가 서비스에서 직접 설정한 닉네임

두 값의 변경 주체와 생명주기가 다르므로 DB 컬럼부터 분리해야 한다.

---

## 3. 구현 순서

다음 순서로 구현하면 각 계층의 역할을 이해하기 쉽다.

1. Flyway 마이그레이션으로 DB 컬럼을 분리한다.
2. `User` 엔티티를 변경한다.
3. 카카오 로그인 로직이 서비스 닉네임을 덮어쓰지 않게 한다.
4. 요청 DTO와 응답 DTO를 만든다.
5. 프로필 Service를 만든다.
6. 프로필 Controller를 만든다.
7. 새 모임과 새 참여자에게 표시 닉네임을 사용한다.
8. CORS에 `PATCH`를 허용한다.
9. 단위 테스트와 API 테스트를 실행한다.

## 4. DB 마이그레이션

새 파일:

`backend/src/main/resources/db/migration/V20__separate_kakao_and_service_nickname.sql`

현재 프로젝트의 마지막 마이그레이션이 V19이므로 V20을 사용한다.

```sql
ALTER TABLE users RENAME COLUMN name TO kakao_nickname;

ALTER TABLE users ADD nickname VARCHAR2(50);
```

### 왜 기존 `name` 컬럼을 rename하는가?

기존 `name`에는 이미 카카오에서 받은 닉네임이 저장되어 있다. 컬럼을 삭제하고 새로 만들면 기존 데이터가 사라질 수 있다. 이름만 `kakao_nickname`으로 바꾸면 데이터와 `NOT NULL` 제약조건을 보존할 수 있다.

### 왜 `nickname`은 NULL을 허용하는가?

모든 회원이 서비스 닉네임을 설정해야 하는 것은 아니다. `NULL`은 “서비스 닉네임을 설정하지 않음”이라는 명확한 상태다. 이때 카카오 닉네임을 대신 표시한다.

### 왜 두 닉네임의 길이를 모두 50자로 맞추는가?

카카오 닉네임과 서비스 닉네임은 용도는 다르지만 둘 다 사용자에게 표시되는 이름이다. 별도의 20자 제한 기획이 없으므로 두 컬럼을 50자로 통일하면 다음 장점이 있다.

- 카카오 닉네임을 그대로 서비스 닉네임으로 설정할 때 길이 제한이 충돌하지 않는다.
- DTO, Entity, DB의 제약조건을 동일하게 유지할 수 있다.
- 긴 닉네임의 화면 표시 문제는 프런트엔드의 말줄임 처리로 해결할 수 있다.

### 주의사항

이미 다른 환경에서 V20이 실행된 적이 있다면 동일 번호를 다시 사용하면 안 된다. 그 환경의 `flyway_schema_history`를 확인하고 아직 사용하지 않은 다음 버전 번호를 선택한다.

## 5. User 엔티티 변경

파일:

`backend/src/main/java/com/makeapp/backend/entity/User.java`

전체 코드를 다음과 같이 변경한다.

```java
package com.makeapp.backend.entity;

import org.hibernate.annotations.SQLRestriction;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.SequenceGenerator;
import jakarta.persistence.Table;
import lombok.AccessLevel;
import lombok.Builder;
import lombok.Getter;
import lombok.NoArgsConstructor;

@Entity
@Table(name = "USERS")
@SQLRestriction("deleted_at IS NULL")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class User extends BaseEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "user_seq")
    @SequenceGenerator(name = "user_seq", sequenceName = "SEQ_USERS", allocationSize = 50)
    private Long id;

    @Column(name = "kakao_id", nullable = false, unique = true, length = 50)
    private String kakaoId;

    @Column(name = "kakao_nickname", nullable = false, length = 50)
    private String kakaoNickname;

    @Column(name = "nickname", length = 50)
    private String nickname;

    @Builder
    public User(String kakaoId, String kakaoNickname, String nickname) {
        this.kakaoId = kakaoId;
        this.kakaoNickname = kakaoNickname;
        this.nickname = nickname;
    }

    public String getDisplayName() {
        return nickname != null && !nickname.isBlank()
                ? nickname
                : kakaoNickname;
    }

    public void updateKakaoNickname(String kakaoNickname) {
        this.kakaoNickname = kakaoNickname;
    }

    public void updateNickname(String nickname) {
        this.nickname = nickname;
    }

}
```

### 메서드를 엔티티에 두는 이유

`getDisplayName()`을 Controller나 Service마다 직접 구현하면 어떤 곳은 서비스 닉네임을 사용하고 어떤 곳은 카카오 닉네임을 사용하는 문제가 생기기 쉽다. 표시 이름 결정 규칙을 `User` 한 곳에 두면 모든 계층이 같은 규칙을 사용한다.

필드를 직접 변경하는 setter 대신 `updateNickname`처럼 의도를 나타내는 메서드를 사용하면 어떤 상태 변경인지 코드에서 바로 알 수 있다.

## 6. 카카오 로그인 로직 변경

파일:

`backend/src/main/java/com/makeapp/backend/service/AuthService.java`

`kakaoLogin` 안의 닉네임 처리 부분을 다음과 같이 변경한다.

기존:

```java
String name = extractNickname(kakaoUser);

User user = userRepository.findByKakaoId(kakaoId)
        .orElseGet(() -> userRepository.save(
                User.builder().kakaoId(kakaoId).name(name).build()));
user.updateName(name);
```

변경:

```java
String kakaoNickname = extractNickname(kakaoUser);

User user = userRepository.findByKakaoId(kakaoId)
        .orElseGet(() -> userRepository.save(
                User.builder()
                        .kakaoId(kakaoId)
                        .kakaoNickname(kakaoNickname)
                        .build()));

user.updateKakaoNickname(kakaoNickname);
```

로그인 응답도 표시 이름을 사용하도록 변경한다.

기존:

```java
new AuthResponse.UserInfo(user.getId(), user.getName())
```

변경:

```java
new AuthResponse.UserInfo(user.getId(), user.getDisplayName())
```

### 왜 로그인할 때 카카오 닉네임은 갱신하는가?

사용자가 카카오에서 닉네임을 바꿀 수 있기 때문이다. 서비스 닉네임을 설정하지 않은 사용자는 최신 카카오 닉네임을 보게 해야 한다.

### 왜 서비스 닉네임은 갱신하지 않는가?

서비스 닉네임은 사용자가 이 서비스에서 직접 정한 값이다. 외부 제공자인 카카오의 프로필 변경이 이 값을 덮어쓰면 사용자의 선택이 사라진다.

## 7. 닉네임 수정 요청 DTO

새 파일:

`backend/src/main/java/com/makeapp/backend/dto/request/UpdateMyProfileRequest.java`

```java
package com.makeapp.backend.dto.request;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;
import lombok.Getter;
import lombok.NoArgsConstructor;

@Getter
@NoArgsConstructor
public class UpdateMyProfileRequest {

    @NotBlank(message = "닉네임을 입력해 주세요.")
    @Size(min = 2, max = 50, message = "닉네임은 2자 이상 50자 이하로 입력해 주세요.")
    private String nickname;
}
```

### DTO에서 검증하는 이유

잘못된 요청을 Controller 진입 시점에 거절할 수 있다. `@Valid`와 함께 사용하면 빈 문자열이나 지나치게 긴 값이 Service까지 전달되지 않는다.

다만 `@Size`는 공백 제거 전 문자열을 검사한다. 예를 들어 `"  한  "`은 원본 길이는 5지만 trim 이후에는 1자다. 따라서 Service에서도 정규화 이후 길이를 다시 검사한다.

## 8. 내 정보 응답 DTO

새 파일:

`backend/src/main/java/com/makeapp/backend/dto/response/MyProfileResponse.java`

```java
package com.makeapp.backend.dto.response;

import com.makeapp.backend.entity.User;

import lombok.Builder;
import lombok.Getter;

@Getter
@Builder
public class MyProfileResponse {

    private Long id;
    private String kakaoNickname;
    private String nickname;
    private String displayName;

    public static MyProfileResponse of(User user) {
        return MyProfileResponse.builder()
                .id(user.getId())
                .kakaoNickname(user.getKakaoNickname())
                .nickname(user.getNickname())
                .displayName(user.getDisplayName())
                .build();
    }
}
```

응답 예시:

```json
{
  "success": true,
  "data": {
    "id": 1,
    "kakaoNickname": "홍길동",
    "nickname": "회의왕",
    "displayName": "회의왕"
  },
  "error": null
}
```

각 필드의 의미:

- `kakaoNickname`: 카카오에서 마지막으로 받은 닉네임
- `nickname`: 서비스에서 직접 설정한 닉네임, 미설정이면 `null`
- `displayName`: 실제 화면에서 우선 표시해야 하는 최종 닉네임

프런트엔드는 표시 규칙을 다시 구현하지 않고 `displayName`을 사용하면 된다.

## 9. MyService 구현

새 파일:

`backend/src/main/java/com/makeapp/backend/service/MyService.java`

```java
package com.makeapp.backend.service;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import com.makeapp.backend.dto.response.MyProfileResponse;
import com.makeapp.backend.entity.User;
import com.makeapp.backend.exception.CustomException;
import com.makeapp.backend.exception.ErrorCode;
import com.makeapp.backend.repository.UserRepository;

import lombok.RequiredArgsConstructor;

@Service
@RequiredArgsConstructor
public class MyService {

    private final UserRepository userRepository;

    @Transactional(readOnly = true)
    public MyProfileResponse getProfile(Long userId) {
        return MyProfileResponse.of(findUser(userId));
    }

    @Transactional
    public MyProfileResponse updateNickname(Long userId, String nickname) {
        User user = findUser(userId);

        String normalizedNickname = nickname == null ? "" : nickname.trim();
        if (normalizedNickname.length() < 2 || normalizedNickname.length() > 50) {
            throw new CustomException(ErrorCode.INVALID_REQUEST);
        }

        user.updateNickname(normalizedNickname);
        return MyProfileResponse.of(user);
    }

    private User findUser(Long userId) {
        return userRepository.findById(userId)
                .orElseThrow(() -> new CustomException(ErrorCode.UNAUTHORIZED));
    }
}
```

### `save()`를 다시 호출하지 않아도 되는 이유

`@Transactional` 안에서 Repository로 조회한 `User`는 JPA 영속 상태다. 필드를 변경하면 트랜잭션이 끝날 때 dirty checking으로 UPDATE 쿼리가 실행된다.

### trim 이후 다시 검사하는 이유

저장 값은 `"  닉네임  "`이 아니라 `"닉네임"`이어야 한다. 저장할 최종 값을 기준으로 길이를 검사해야 DTO 검증의 공백 우회 문제를 막을 수 있다.

### 조회에 `readOnly = true`를 사용하는 이유

조회 목적임을 명확히 표현하고 불필요한 변경 감지 비용을 줄일 수 있다.

## 10. MyController 구현

새 파일:

`backend/src/main/java/com/makeapp/backend/controller/MyController.java`

```java
package com.makeapp.backend.controller;

import org.springframework.http.ResponseEntity;
import org.springframework.security.core.Authentication;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PatchMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import com.makeapp.backend.common.ApiResponse;
import com.makeapp.backend.dto.request.UpdateMyProfileRequest;
import com.makeapp.backend.dto.response.MyProfileResponse;
import com.makeapp.backend.exception.CustomException;
import com.makeapp.backend.exception.ErrorCode;
import com.makeapp.backend.service.MyService;

import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;

@RestController
@RequestMapping("/api/my")
@RequiredArgsConstructor
public class MyController {

    private final MyService myService;

    @GetMapping("/profile")
    public ResponseEntity<ApiResponse<MyProfileResponse>> getProfile(
            Authentication authentication) {
        return ResponseEntity.ok(ApiResponse.ok(
                myService.getProfile(memberId(authentication))));
    }

    @PatchMapping("/profile")
    public ResponseEntity<ApiResponse<MyProfileResponse>> updateProfile(
            @RequestBody @Valid UpdateMyProfileRequest request,
            Authentication authentication) {
        return ResponseEntity.ok(ApiResponse.ok(
                myService.updateNickname(
                        memberId(authentication),
                        request.getNickname())));
    }

    private Long memberId(Authentication authentication) {
        boolean guest = authentication.getAuthorities().stream()
                .anyMatch(authority ->
                        "ROLE_GUEST".equals(authority.getAuthority()));

        if (guest) {
            throw new CustomException(ErrorCode.FORBIDDEN);
        }

        return (Long) authentication.getPrincipal();
    }
}
```

### `Authentication`에서 ID를 가져오는 이유

현재 `JwtAuthFilter`는 카카오 회원 JWT의 `userId`를 principal에 넣는다. 요청 body나 URL에서 회원 ID를 받으면 다른 회원의 ID로 요청을 조작할 수 있다. 인증된 JWT에서 ID를 꺼내야 항상 로그인한 본인의 정보만 수정한다.

### 게스트를 거부하는 이유

게스트 JWT의 principal은 `userId`가 아니라 `participantId`다. 둘 다 `Long`이라 그대로 사용하면 우연히 같은 ID를 가진 회원을 조회할 위험이 있다. `ROLE_GUEST`를 확인해 명시적으로 403을 반환해야 한다.

## 11. 새 모임과 새 참여자의 표시 이름 변경

서비스 닉네임을 수정해도 실제 사용처에서 계속 카카오 닉네임을 읽으면 기능이 완성되지 않는다.

### MeetingService

파일:

`backend/src/main/java/com/makeapp/backend/service/MeetingService.java`

기존:

```java
.displayName(user.getName())
```

변경:

```java
.displayName(user.getDisplayName())
```

### ParticipantService

파일:

`backend/src/main/java/com/makeapp/backend/service/ParticipantService.java`

기존:

```java
String displayName = (customDisplayName != null && !customDisplayName.isBlank())
        ? customDisplayName
        : user.getName();
```

변경:

```java
String displayName = (customDisplayName != null && !customDisplayName.isBlank())
        ? customDisplayName
        : user.getDisplayName();
```

### MeetingDetailResponse

파일:

`backend/src/main/java/com/makeapp/backend/dto/response/MeetingDetailResponse.java`

기존:

```java
this.ownerName = meeting.getOwner().getName();
```

변경:

```java
this.ownerName = meeting.getOwner().getDisplayName();
```

### 기존 Participant 이름을 일괄 변경하지 않는 이유

`Participant.displayName`은 모임에 참여한 당시의 이름 스냅샷이다. 닉네임을 바꿀 때 과거 모든 모임의 참여자 이름까지 바꾸면 과거 기록과 당시 단톡방에서 알던 이름이 달라질 수 있다.

따라서 정책은 다음처럼 잡는다.

- 이미 만들어진 Participant: 기존 `displayName` 유지
- 닉네임 변경 후 새로 생성되는 Participant: 새 `displayName` 사용

## 12. CORS 설정 변경

파일:

`backend/src/main/java/com/makeapp/backend/config/SecurityConfig.java`

기존:

```java
config.setAllowedMethods(List.of("GET", "POST", "PUT", "OPTIONS"));
```

변경:

```java
config.setAllowedMethods(
        List.of("GET", "POST", "PUT", "PATCH", "OPTIONS"));
```

브라우저에서 프런트엔드와 백엔드의 origin이 다르면 `PATCH` 전에 preflight 요청이 발생할 수 있다. 서버에 API가 구현되어 있어도 CORS 허용 목록에 메서드가 없으면 브라우저가 요청을 차단한다.

`/api/my/**`는 현재 `anyRequest().authenticated()` 규칙으로도 인증이 필요하다. 더 명확하게 표현하고 싶다면 다음 규칙을 추가할 수 있다.

```java
.requestMatchers("/api/my/**").authenticated()
```

이 규칙은 공개 API 규칙보다 뒤로 밀리지 않게 배치한다.

import static org.assertj.core.api.Assertions.assertThatThrownBy;

import com.makeapp.backend.exception.ErrorCode;

    @Test
    void nicknameLengthIsValidatedAfterTrimming() {

                .kakaoId("123")

## 16. 구현 후 자주 발생하는 오류

### `ORA-00904: NAME: invalid identifier`

마이그레이션으로 컬럼은 `kakao_nickname`이 되었는데 Entity나 SQL 어딘가에서 아직 `name`을 참조하는 경우다.

다음 검색으로 남은 참조를 확인한다.

```powershell
rg "user\.getName|User\.builder|updateName|u\.name" backend/src
```

V19처럼 과거에 이미 실행된 마이그레이션 파일에서 `u.name`이 발견되는 것은 정상이다. 기존 migration은 수정하면 안 된다. V19가 먼저 실행되고 V20에서 rename되기 때문이다.

### 서비스 닉네임이 로그인 후 사라짐

`AuthService.kakaoLogin()`에서 `updateNickname(kakaoNickname)`을 호출했는지 확인한다. 로그인에서는 반드시 `updateKakaoNickname()`만 호출해야 한다.

### Postman에서는 되지만 브라우저에서는 실패

`SecurityConfig`의 CORS 허용 메서드에 `PATCH`가 있는지 확인한다. 프런트 요청에 쿠키 전송 옵션도 필요하다.

```javascript
fetch("/api/my/profile", {
  method: "PATCH",
  credentials: "include",
  headers: {
    "Content-Type": "application/json"
  },
  body: JSON.stringify({ nickname: "회의왕" })
});
```

### 게스트 요청에서 엉뚱한 회원이 조회됨

회원 JWT principal은 `userId`, 게스트 JWT principal은 `participantId`다. Controller에서 `ROLE_GUEST`를 검사하지 않고 principal을 회원 ID로 사용하면 발생할 수 있다.
