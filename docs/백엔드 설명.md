# make-app 백엔드 개발 가이드 — 기능 단위 Postman 검증

## Context

엔티티 레이어가 완성된 상태에서, **기능 하나씩 완성하면서 Postman으로 즉시 검증**하는 방식으로 개발한다.
레이어 단위(Repository 전체 → DTO 전체 → ...)가 아닌, 수직 슬라이스(Vertical Slice)로 진행한다.

- 인증 방식: **카카오 OAuth + JWT** (Access Token 1시간, Refresh Token 7일), 토큰은 **HttpOnly Cookie**로 관리
- 비회원 인증: 닉네임 + 4자리 PIN 해시 → 게스트 JWT 발급 (HttpOnly Cookie 저장)

---

## 개발 흐름

> 🤔 **수직 슬라이스(Vertical Slice)가 뭐예요? 왜 기능 단위로 개발하나요?**
> "Repository 전부 → DTO 전부 → Service 전부 → Controller 전부" 처럼 **층(layer)별로** 만들면, 맨 마지막에 Controller를 붙이기 전까지는 아무것도 실행해볼 수 없다. 버그가 쌓여 있다가 한꺼번에 터진다.
> 대신 **기능 하나(예: 카카오 로그인)를 DTO→Service→Controller까지 세로로 관통**해서 완성하고 바로 Postman으로 검증하면, 동작하는 코드를 빠르게 확인하며 한 걸음씩 나아갈 수 있다. 이게 현업에서 말하는 수직 슬라이스이고, 이 문서가 Phase 1~8을 기능 단위로 나눈 이유다.

```
Phase 0: 공통 기반 (Entity, Exception, Repository)
   ↓
Phase 1: 카카오 로그인 + JWT 발급/검증 → Postman 검증
   ↓
Phase 2: 모임 생성 → Postman 검증
   ↓
Phase 3: 모임 조회 → Postman 검증
   ↓
Phase 4: 참가자 등록 → Postman 검증
   ↓
Phase 5: 가용 시간 제출 → Postman 검증
   ↓
Phase 6: 결과 조회 + 추천 → Postman 검증
   ↓
Phase 7: 모임 확정 / 만료 / 취소 → Postman 검증
   ↓
Phase 8: 내 모임 목록 → Postman 검증
```

---

> 🤔 **수직 슬라이스라면서 왜 Phase 0에서 엔티티·Repository를 미리 다 만드나요?**
> 엔티티(=DB 테이블 구조)와 Repository는 **모든 기능이 공유하는 토대**다. 기능을 만들 때마다 테이블을 새로 설계하면 앞 기능과 충돌하기 쉽다. 그래서 도메인 모델(엔티티)은 먼저 한 번에 굳혀 두는 게 일반적이다. Repository도 인터페이스 한 줄짜리라 미리 선언해 두면 기능 개발 중 왔다 갔다 하는 수고가 줄어든다. (엄격한 수직 슬라이스라면 Repository 메서드도 기능별로 그때그때 추가한다 — 지금은 학습 편의를 위해 모아 둔 것이다.)

## entity/BaseEntity.java

> 🤔 **왜 BaseEntity를 따로 만들고 `@MappedSuperclass` + Auditing을 쓰나요?**
> 거의 모든 테이블에 "생성/수정/삭제 시각"이 필요하다. 이걸 엔티티마다 복붙하면 중복이 쌓인다. `@MappedSuperclass`로 공통 필드를 부모 클래스에 모아 두면 자식 엔티티가 상속만으로 컬럼을 갖는다. 여기에 JPA Auditing(`@CreatedDate`/`@LastModifiedDate` + `BackendApplication`의 `@EnableJpaAuditing`)을 붙이면 `createdAt`/`updatedAt`을 **save/update 시 자동으로 채워 준다** — 직접 세팅할 필요가 없다.
>
> 🤔 **왜 `deleted_at`을 두고 진짜 DELETE를 안 하나요? (Soft Delete)**
> 사용자가 모임을 지워도 데이터를 물리적으로 삭제하지 않고 `deleted_at`에 삭제 시각만 기록한다. 실수로 지운 걸 복구하거나 통계를 보존할 수 있고, 다른 테이블이 참조 중이어도 안전하다. 대신 조회할 때 삭제된 행을 매번 걸러야 하는데, 그건 각 엔티티의 `@SQLRestriction("deleted_at IS NULL")`이 자동으로 처리한다(아래 User 참고).

```java
package com.makeapp.backend.entity;

import jakarta.persistence.Column;
import jakarta.persistence.EntityListeners;
import jakarta.persistence.MappedSuperclass;
import lombok.Getter;
import org.springframework.data.annotation.CreatedDate;
import org.springframework.data.annotation.LastModifiedDate;
import org.springframework.data.jpa.domain.support.AuditingEntityListener;

import java.time.LocalDateTime;

@Getter                                          // Lombok: 모든 필드의 getter를 자동 생성
@MappedSuperclass                                // 이 클래스는 테이블이 아니라, 상속한 엔티티에 컬럼만 물려줌
@EntityListeners(AuditingEntityListener.class)   // 저장/수정 시점을 감지해 아래 시각 필드를 자동으로 채워줌
public abstract class BaseEntity {

    @CreatedDate                                 // 처음 저장될 때 현재 시각이 자동 입력됨
    @Column(name = "created_at", updatable = false)  // 생성 시각은 이후 수정되지 않도록 막음
    private LocalDateTime createdAt;

    @LastModifiedDate                            // 수정될 때마다 현재 시각으로 자동 갱신됨
    @Column(name = "updated_at")
    private LocalDateTime updatedAt;

    @Column(name = "deleted_at")                 // 값이 있으면 "삭제됨", null이면 "살아있음" (Soft Delete)
    private LocalDateTime deletedAt;

    // 실제로 행을 지우는 대신 삭제 시각만 기록한다 (물리 삭제 X → Soft Delete)
    public void delete() {
        this.deletedAt = LocalDateTime.now();
    }
}
```

## entity/User.java

> 🤔 **왜 `@NoArgsConstructor(access = PROTECTED)` + `@Builder`를 쓰나요?**
> JPA는 엔티티를 만들 때 기본 생성자가 *필요*하지만, 아무 데서나 `new User()`로 빈 객체를 만들면 필수값이 빠진 불완전한 엔티티가 돌아다닌다. 기본 생성자를 `protected`로 막아 외부 사용을 차단하고, 객체 생성은 어떤 값이 필수인지 한눈에 보이는 `@Builder`로만 하게 만든다.
>
> 🤔 **`@SQLRestriction("deleted_at IS NULL")`은 뭔가요?**
> 이 엔티티를 조회하는 모든 쿼리에 자동으로 `WHERE deleted_at IS NULL`을 붙여 준다. 덕분에 Soft Delete된 행은 `findAll`, `findById` 등에서 알아서 제외된다 — 매 쿼리에 조건을 직접 쓰지 않아도 된다.
>
> 🤔 **`@SequenceGenerator`의 `allocationSize = 50`은 왜 50인가요?**
> Oracle 시퀀스에서 ID를 하나 받을 때마다 DB를 왕복하면 느리다. `allocationSize = 50`은 "한 번에 50개의 번호를 미리 받아 두고 메모리에서 나눠 쓴다"는 뜻이라 DB 왕복이 50번에 1번으로 줄어 INSERT가 빨라진다. (DB 시퀀스의 increment 설정과 값을 맞춰야 한다.)

```java
package com.makeapp.backend.entity;

import jakarta.persistence.*;
import lombok.AccessLevel;
import lombok.Builder;
import lombok.Getter;
import lombok.NoArgsConstructor;
import org.hibernate.annotations.SQLRestriction;

@Entity                                          // JPA가 관리하는 DB 테이블 매핑 클래스
@Table(name = "USERS")                           // 매핑할 테이블 이름 (user는 예약어라 USERS 사용)
@SQLRestriction("deleted_at IS NULL")            // 조회 시 자동으로 "삭제 안 된 행"만 가져옴
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)  // 기본 생성자를 막아 아무 데서나 new User() 못 하게 함
public class User extends BaseEntity {            // BaseEntity의 created/updated/deleted 컬럼을 물려받음

    @Id                                          // 기본 키(PK)
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "user_seq")  // 시퀀스로 ID 자동 생성
    @SequenceGenerator(name = "user_seq", sequenceName = "SEQ_USERS", allocationSize = 50)  // 50개씩 미리 받아 성능↑
    private Long id;

    @Column(name = "kakao_id", nullable = false, unique = true, length = 50)  // 카카오 회원 식별값, 중복 불가
    private String kakaoId;

    @Column(nullable = false, length = 50)       // 필수값(NOT NULL), 최대 50자
    private String name;

    @Builder                                     // User.builder().kakaoId(..).name(..).build() 형태로 생성
    public User(String kakaoId, String name) {
        this.kakaoId = kakaoId;
        this.name = name;
    }

    public void updateName(String name) {        // 이름 변경은 setter 대신 의미 있는 메서드로만 허용
        this.name = name;
    }
}
```

## entity/MeetingStatus.java

> 🤔 **왜 상태값을 String이 아니라 enum으로 따로 만드나요?**
> 모임 상태를 그냥 문자열("OPEN")로 다루면 오타("OPNE")가 컴파일 시점에 안 걸리고 런타임에야 터진다. enum으로 두면 정해진 값만 쓸 수 있어 **타입 안전**하고, 자동완성도 된다. 엔티티에서 `@Enumerated(EnumType.STRING)`으로 매핑하면 DB에도 `"OPEN"` 문자열로 저장돼 사람이 읽기 좋다. (`EnumType.ORDINAL`은 0,1,2 숫자로 저장돼 enum 순서를 바꾸면 기존 데이터가 깨지므로 STRING을 쓴다.)

```java
package com.makeapp.backend.entity;

public enum MeetingStatus {
    OPEN,        // 모집 중 (가용 시간 받는 단계)
    CONFIRMED,   // 모임 시간 확정됨
    EXPIRED      // 만료/종료됨
}
```

## entity/Meeting.java

> 🤔 **`@ManyToOne(fetch = FetchType.LAZY)`는 왜 항상 LAZY로 두나요?**
> 연관 엔티티를 `EAGER`(기본값)로 두면 Meeting 하나를 조회할 때 owner(User)까지 매번 즉시 함께 조회된다. 목록을 N개 가져오면 연관 조회가 N번 더 나가는 **N+1 문제**의 원인이 된다. `LAZY`는 실제로 `meeting.getOwner()`를 호출하는 순간에만 조회하므로, 필요 없을 때 불필요한 쿼리를 막는다. 그래서 `@ManyToOne`/`@OneToOne`은 LAZY로 두는 것이 정석이다.
>
> 🤔 **왜 비즈니스 동작(`confirm`, `expire`)을 엔티티 안에 메서드로 넣나요?**
> 상태를 바꾸는 규칙(확정하면 `status`가 CONFIRMED가 된다 등)을 엔티티가 직접 갖고 있으면, 상태 변경이 항상 이 메서드를 거치게 되어 규칙이 한곳에 모인다. 서비스에서 `setStatus(...)` 같은 setter를 열어 두면 아무 데서나 상태를 바꿔 버려 일관성이 깨진다. 그래서 setter 대신 의미 있는 메서드만 공개한다.

```java
package com.makeapp.backend.entity;

import jakarta.persistence.*;
import lombok.AccessLevel;
import lombok.Builder;
import lombok.Getter;
import lombok.NoArgsConstructor;
import org.hibernate.annotations.SQLRestriction;

@Entity
@Table(name = "MEETINGS")
@SQLRestriction("deleted_at IS NULL")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Meeting extends BaseEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "meeting_seq")
    @SequenceGenerator(name = "meeting_seq", sequenceName = "SEQ_MEETINGS", allocationSize = 50)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)           // 모임 N개 : 주최자 1명 관계, 실제 쓸 때만 조회(LAZY)
    @JoinColumn(name = "owner_id", nullable = false)  // DB의 owner_id 외래키(FK) 컬럼과 연결
    private User owner;                           // 모임을 만든 사람(주최자)

    @Column(nullable = false, length = 50)
    private String name;                          // 모임 이름

    @Column(name = "expected_count")
    private Integer expectedCount;                // 예상 참가 인원 (선택값이라 nullable)

    @Column(name = "invite_token", nullable = false, unique = true, length = 36)
    private String inviteToken;                   // 참가용 초대 링크 토큰 (UUID, 36자)

    @Column(name = "result_token", nullable = false, unique = true, length = 36)
    private String resultToken;                   // 결과 공유용 토큰 (참가용과 권한 분리)

    @Enumerated(EnumType.STRING)                  // enum을 숫자가 아닌 문자열("OPEN")로 DB에 저장
    @Column(nullable = false, length = 20)
    private MeetingStatus status;                 // 모임 상태 (OPEN/CONFIRMED/EXPIRED)

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "confirmed_slot_id")       // 확정된 후보 시간 (확정 전엔 null)
    private CandidateSlot confirmedSlot;

    @Builder
    public Meeting(User owner, String name, Integer expectedCount,
                   String inviteToken, String resultToken) {
        this.owner = owner;
        this.name = name;
        this.expectedCount = expectedCount;
        this.inviteToken = inviteToken;
        this.resultToken = resultToken;
        this.status = MeetingStatus.OPEN;         // 새 모임은 항상 OPEN 상태로 시작
    }

    // 시간 확정: 확정 슬롯을 지정하고 상태를 CONFIRMED로 변경 (상태 변경 규칙을 엔티티가 직접 관리)
    public void confirm(CandidateSlot slot) {
        this.confirmedSlot = slot;
        this.status = MeetingStatus.CONFIRMED;
    }

    // 만료 처리: 상태만 EXPIRED로 변경
    public void expire() {
        this.status = MeetingStatus.EXPIRED;
    }
}
```

## entity/CandidateSlot.java

```java
package com.makeapp.backend.entity;

import jakarta.persistence.*;
import lombok.AccessLevel;
import lombok.Builder;
import lombok.Getter;
import lombok.NoArgsConstructor;
import org.hibernate.annotations.SQLRestriction;

import java.time.LocalDate;
import java.time.LocalTime;

@Entity
@Table(name = "CANDIDATE_SLOTS")
@SQLRestriction("deleted_at IS NULL")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class CandidateSlot extends BaseEntity {  // 모임의 후보 시간대 하나 (예: 7/1 18:00~20:00)

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "candidate_slot_seq")
    @SequenceGenerator(name = "candidate_slot_seq", sequenceName = "SEQ_CANDIDATE_SLOTS", allocationSize = 50)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "meeting_id", nullable = false)  // 어느 모임의 후보 시간인지 (FK)
```

## entity/Participant.java

> 🤔 **PIN 잠금(`incrementPinFail`, `isPinLocked`)이나 `@PrePersist validate` 같은 로직을 왜 엔티티에 두나요?**
> "PIN 5회 틀리면 30분 잠금", "회원도 PIN도 없는 참가자는 만들 수 없다" 같은 규칙은 Participant라는 도메인 자체의 불변 규칙이다. 이 규칙을 서비스 곳곳에 흩어 두면 빠뜨리기 쉽다. 엔티티가 자기 규칙을 직접 들고 있으면(이걸 "도메인 응집"이라 한다) 어디서 호출하든 규칙이 일관되게 지켜진다.
> - `@PrePersist`/`@PreUpdate`: 저장·수정 직전에 JPA가 자동으로 `validate()`를 호출해, 잘못된 상태의 엔티티가 DB에 들어가는 걸 막는다.
> - `pinHash`: PIN을 평문이 아니라 **해시값**으로 저장한다(이유는 Phase 1-A의 `BCryptPasswordEncoder` 설명 참고).

```java
package com.makeapp.backend.entity;

import com.makeapp.backend.exception.CustomException;
import com.makeapp.backend.exception.ErrorCode;
import jakarta.persistence.*;
import lombok.AccessLevel;
import lombok.Builder;
import lombok.Getter;
import lombok.NoArgsConstructor;
import org.hibernate.annotations.SQLRestriction;

import java.time.LocalDateTime;

@Entity
@Table(name = "PARTICIPANTS")
@SQLRestriction("deleted_at IS NULL")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Participant extends BaseEntity {     // 한 모임에 참여한 사람 1명 (회원이거나 게스트)

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "participant_seq")
    @SequenceGenerator(name = "participant_seq", sequenceName = "SEQ_PARTICIPANTS", allocationSize = 50)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "meeting_id", nullable = false)  // 어느 모임의 참가자인지 (FK, 필수)
    private Meeting meeting;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")                 // 회원이면 User 연결, 게스트면 null
    private User user;

    @Column(name = "pin_hash", length = 255)      // 게스트의 PIN 해시값 (회원이면 null), 평문 저장 X
    private String pinHash;

    @Column(name = "pin_fail_count", nullable = false)
    private int pinFailCount = 0;                 // PIN 연속 실패 횟수 (5회 시 잠금)

    @Column(name = "pin_locked_until")
    private LocalDateTime pinLockedUntil;         // 이 시각까지 잠금 (null이면 잠기지 않음)

    @Column(name = "display_name", nullable = false, length = 50)
    private String displayName;                   // 모임 안에서 보이는 이름 (모임 내 중복 불가)

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private ParticipantType type;                 // LEADER / MEMBER / GUEST

    @Column(name = "submitted_at")
    private LocalDateTime submittedAt;            // 가용 시간 제출 완료 시각 (null이면 미제출)

    @Builder
    public Participant(Meeting meeting, User user, String pinHash,
                       String displayName, ParticipantType type) {
        this.meeting = meeting;
        this.user = user;
        this.pinHash = pinHash;
        this.displayName = displayName;
        this.type = type;
    }

    // 가용 시간 제출 완료 처리 (제출 시각 기록)
    public void submit() {
        this.submittedAt = LocalDateTime.now();
    }

    // 제출했는지 여부 (제출 시각이 있으면 true)
    public boolean isSubmitted() {
        return this.submittedAt != null;
    }

    // 현재 PIN이 잠겨 있는지 (잠금 시각이 있고, 아직 그 시각 전이면 잠김)
    public boolean isPinLocked() {
        return pinLockedUntil != null && LocalDateTime.now().isBefore(pinLockedUntil);
    }

    // PIN 틀릴 때마다 실패 횟수 +1, 5회 이상이면 30분 잠금
    public void incrementPinFail() {
        this.pinFailCount++;
        if (this.pinFailCount >= 5) {
            this.pinLockedUntil = LocalDateTime.now().plusMinutes(30);
        }
    }

    // PIN 성공 시 실패 기록 초기화
    public void resetPinFail() {
        this.pinFailCount = 0;
        this.pinLockedUntil = null;
    }

    public void updatePinHash(String pinHash) {
        this.pinHash = pinHash;
    }

    // 저장/수정 직전에 JPA가 자동 호출: 회원도 아니고 PIN도 없는 "정체불명" 참가자를 막음
    @PrePersist
    @PreUpdate
    private void validate() {
        if (user == null && pinHash == null) {
            throw new CustomException(ErrorCode.UNAUTHORIZED);
        }
    }
}
```

## common/ApiResponse.java

> 🤔 **왜 응답을 `ApiResponse<T>`로 한 번 감싸나요? 그냥 데이터만 주면 안 되나요?**
> API마다 어떤 건 데이터를 그대로, 어떤 건 에러를 다른 모양으로 주면 프론트엔드가 응답을 처리하는 코드를 매번 다르게 짜야 한다. 모든 응답을 `{ success, data, error }`라는 **하나의 포맷**으로 통일하면, 프론트는 항상 `success`만 먼저 보고 분기하면 된다. 제네릭 `<T>`는 `data`에 어떤 타입(AuthResponse, MeetingResponse...)이든 담을 수 있게 해 준다.

```java
package com.makeapp.backend.common;

import lombok.Getter;

@Getter
public class ApiResponse<T> {                    // <T>: data에 어떤 타입이든 담을 수 있는 제네릭

    private final boolean success;               // 성공 여부 (프론트가 가장 먼저 확인)
    private final T data;                         // 성공 시 실제 데이터 (실패면 null)
    private final ErrorInfo error;               // 실패 시 에러 정보 (성공이면 null)

    // 생성자를 private으로 막고, 아래 static 메서드로만 만들게 함 (의도를 분명히)
    private ApiResponse(boolean success, T data, ErrorInfo error) {
        this.success = success;
        this.data = data;
        this.error = error;
    }

    // 데이터가 있는 성공 응답
    public static <T> ApiResponse<T> ok(T data) {
        return new ApiResponse<>(true, data, null);
    }

    // 반환할 데이터가 없는 성공 응답 (예: 로그아웃)
    public static ApiResponse<Void> ok() {
        return new ApiResponse<>(true, null, null);
    }

    // 실패 응답 (에러 코드 + 메시지)
    public static ApiResponse<Void> fail(String code, String message) {
        return new ApiResponse<>(false, null, new ErrorInfo(code, message));
    }

    @Getter
    public static class ErrorInfo {              // 에러의 코드와 메시지를 담는 작은 내부 클래스
        private final String code;
        private final String message;

        public ErrorInfo(String code, String message) {
            this.code = code;
            this.message = message;
        }
    }
}
```

## exception/ErrorCode.java

> 🤔 **왜 `ErrorCode` enum + `CustomException` + `GlobalExceptionHandler`로 나눠 예외를 처리하나요?**
> 컨트롤러마다 `try-catch`로 에러 응답을 직접 만들면 중복되고, HTTP 상태코드·에러 메시지가 제각각이 된다. 이 셋을 조합하면 예외 처리가 한 줄기로 흐른다.
> - **`ErrorCode`**: "어떤 에러가 있고, 각각 HTTP 상태/코드/메시지가 무엇인가"를 한곳에 정의한 카탈로그.
> - **`CustomException`**: 서비스 로직에서 `throw new CustomException(ErrorCode.XXX)` 한 줄로 에러를 던진다.
> - **`GlobalExceptionHandler`(`@RestControllerAdvice`)**: 던져진 예외를 앱 전역에서 가로채 `ApiResponse.fail(...)` 형태로 변환한다. → 서비스는 "무엇이 잘못됐는지"만 신경 쓰고, "어떻게 응답할지"는 핸들러가 전담한다.

## exception/GlobalExceptionHandler.java

```java
package com.makeapp.backend.exception;

import com.makeapp.backend.common.ApiResponse;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice                            // 앱 전역에서 컨트롤러 예외를 한곳에서 가로채는 클래스
public class GlobalExceptionHandler {

    // 우리가 던진 CustomException 처리 → ErrorCode의 상태/코드/메시지로 응답
    @ExceptionHandler(CustomException.class)
    public ResponseEntity<ApiResponse<Void>> handleCustomException(CustomException e) {
        ErrorCode ec = e.getErrorCode();
        return ResponseEntity
                .status(ec.getStatus())
                .body(ApiResponse.fail(ec.getCode(), ec.getMessage()));
    }

    // @Valid 검증 실패 처리 → 첫 번째 위반 메시지를 400으로 응답
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ApiResponse<Void>> handleValidException(MethodArgumentNotValidException e) {
        String message = e.getBindingResult().getFieldErrors().get(0).getDefaultMessage();
        return ResponseEntity
                .badRequest()                    // 400 Bad Request
                .body(ApiResponse.fail("INVALID_REQUEST", message));
    }
}
```

## repository/UserRepository.java

> 🤔 **Repository는 왜 인터페이스만 있고 구현 코드가 없나요?**
> `JpaRepository`를 상속한 인터페이스를 선언하면, Spring Data JPA가 **실행 시점에 구현 클래스를 자동으로 만들어 준다**. `save`, `findById`, `findAll` 같은 기본 CRUD는 이미 들어 있고, `findByKakaoId`처럼 **메서드 이름만 규칙에 맞게 지으면** 그 이름을 해석해 쿼리(`WHERE kakao_id = ?`)까지 자동 생성한다. 그래서 우리는 "무엇을 찾을지"만 선언하면 된다.
> 아래 Repository들의 메서드는 뒤 Phase에서 필요해질 것을 미리 모아 둔 것이다 — 예: `findByInviteToken`은 Phase 3(모임 조회), `findByMeetingAndDisplayName`은 Phase 1-F(게스트 로그인)에서 쓰인다.

```java
package com.makeapp.backend.repository;

import com.makeapp.backend.entity.User;
import org.springframework.data.jpa.repository.JpaRepository;

import java.util.Optional;

// JpaRepository<엔티티, PK타입>을 상속하면 save/findById/findAll 등 기본 CRUD가 자동 제공됨
public interface UserRepository extends JpaRepository<User, Long> {
    // 메서드 이름만 규칙대로 지으면 "WHERE kakao_id = ?" 쿼리가 자동 생성됨
    // Optional: 결과가 없을 수도 있음을 타입으로 표현 (null 대신)
    Optional<User> findByKakaoId(String kakaoId);
}
```

> 🤔 **엔티티가 있는데 왜 Flyway SQL로 또 테이블을 관리하나요? `ddl-auto`로 자동 생성하면 안 되나요?**
> `ddl-auto: create/update`로 JPA가 테이블을 자동 생성·변경하게 두면 편하지만, **무엇이 어떻게 바뀌는지 예측·추적할 수 없어** 운영 DB에서는 위험하다(컬럼이 통째로 날아갈 수도 있다). Flyway는 `V1, V2... V11`처럼 **번호가 매겨진 SQL 파일로 스키마 변경 이력을 코드처럼 버전 관리**한다. 팀원 누구나 같은 순서로 같은 스키마를 재현할 수 있다.
> 그래서 이 프로젝트는 `ddl-auto: validate`(JPA는 엔티티와 실제 테이블이 **일치하는지 검사만** 하고 건드리지 않음) + Flyway(실제 스키마 변경 담당) 조합을 쓴다. 엔티티를 바꾸면 그에 맞는 마이그레이션 SQL도 함께 추가해야 기동 시 validate를 통과한다.

## Phase 1-A — JWT 인프라 (Postman 테스트 없음)

JWT 라이브러리·필터·Security 설정은 이후 모든 인증의 공통 기반이라 한 번에 작성한다.

> 🤔 **기능 단위로 개발한다면서 1-A는 왜 기능 없이 인프라부터 만드나요?**
> 카카오 로그인, 토큰 갱신, 게스트 인증 등 Phase 1의 모든 기능이 "JWT를 만들고 검증한다"는 같은 토대 위에 선다. 이 공통 토대를 기능마다 조금씩 만들면 오히려 중복·혼란이 커진다. 그래서 1-A에서 토대만 먼저 깔고(테스트할 화면이 없으니 Postman 검증도 없음), 1-B부터 실제 기능을 세로로 관통한다.
>
> 🤔 **JWT가 뭐길래 쓰나요?**
> 로그인한 사용자를 매 요청마다 다시 인증하지 않으려면 "이 사람은 누구"라는 증표가 필요하다. 전통적으로는 서버 메모리에 세션을 저장했지만, JWT는 **사용자 정보(userId 등)를 서명해서 토큰 자체에 담는다**. 서버는 토큰의 서명만 검증하면 되므로 세션을 저장할 필요가 없다(=stateless). 서명 키는 서버만 알기에 위조할 수 없다.

### auth/JwtProvider.java

```java
package com.makeapp.backend.auth;

import java.nio.charset.StandardCharsets;
import java.util.Date;

import javax.crypto.SecretKey;

import org.springframework.stereotype.Component;

import com.makeapp.backend.exception.CustomException;
import com.makeapp.backend.exception.ErrorCode;

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.ExpiredJwtException;
import io.jsonwebtoken.JwtException;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;

@Component                                       // 스프링이 관리하는 빈으로 등록 (다른 곳에서 주입받아 사용)
public class JwtProvider {

    private final SecretKey key;                 // 토큰 서명/검증에 쓰는 비밀 키 (서버만 앎)
    private final long accessExpiration;         // access token 수명 (ms)
    private final long refreshExpiration;        // refresh token 수명 (ms)

    // application.yaml의 jwt.* 설정값을 생성자로 주입받아 초기화
    public JwtProvider(
            @Value("${jwt.secret}") String secret,
            @Value("${jwt.access-expiration}") long accessExpiration,
            @Value("${jwt.refresh-expiration}") long refreshExpiration) {
        this.key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));  // 문자열 비밀키 → 서명 키 객체
        this.accessExpiration = accessExpiration;
        this.refreshExpiration = refreshExpiration;
    }

    // 회원용 access token 발급 (subject = userId)
    public String createAccessToken(Long userId) {
        return createToken(String.valueOf(userId), accessExpiration, null, null);
    }

    // 회원용 refresh token 발급 (수명만 더 긺)
    public String createRefreshToken(Long userId) {
        return createToken(String.valueOf(userId), refreshExpiration, null, null);
    }

    // 게스트용 JWT: subject=participantId, claim에 meetingId와 role="GUEST" 포함
    public String createGuestToken(Long participantId, Long meetingId) {
        return createToken(String.valueOf(participantId), accessExpiration, meetingId, "GUEST");
    }

    // 실제 토큰을 만드는 공통 메서드
    private String createToken(String subject, long expiration, Long meetingId, String role) {
        Date now = new Date();
        var builder = Jwts.builder()
                .subject(subject)                        // 토큰 주인 식별값 (userId 또는 participantId)
                .issuedAt(now)                           // 발급 시각
                .expiration(new Date(now.getTime() + expiration));  // 만료 시각 = 지금 + 수명
        if (meetingId != null) builder.claim("meetingId", meetingId);  // 게스트일 때만 추가 정보 담음
        if (role != null) builder.claim("role", role);
        return builder.signWith(key).compact();          // 비밀 키로 서명 후 문자열로 압축 → 위조 불가
    }

    // 토큰에서 userId 꺼내기 (subject를 숫자로 변환)
    public Long getUserId(String token) {
        return Long.parseLong(parseClaims(token).getSubject());
    }

    // 토큰에서 participantId 꺼내기 (게스트 토큰용, subject 위치는 동일)
    public Long getParticipantId(String token) {
        return Long.parseLong(parseClaims(token).getSubject());
    }

    // 게스트 토큰에 담긴 meetingId 꺼내기
    public Long getMeetingId(String token) {
        return parseClaims(token).get("meetingId", Long.class);
    }

    // role claim이 "GUEST"이면 게스트 토큰으로 판단
    public boolean isGuest(String token) {
        return "GUEST".equals(parseClaims(token).get("role", String.class));
    }

    // 예외 대신 boolean 반환 (refreshToken 유효성 사전 체크용)
    public boolean isValid(String token) {
        try {
            parseClaims(token);                  // 파싱/검증 성공하면 유효
            return true;
        } catch (JwtException e) {
            return false;                        // 만료/위조 등 문제 있으면 false
        }
    }

    // 토큰을 검증하고, 문제가 있으면 예외를 던짐 (필터에서 사용)
    public void validate(String token) {
        try {
            parseClaims(token);
        } catch (ExpiredJwtException e) {
            throw new CustomException(ErrorCode.EXPIRED_TOKEN);   // 만료됨 → 재발급 유도
        } catch (JwtException e) {
            throw new CustomException(ErrorCode.INVALID_TOKEN);   // 위조/형식 오류 → 재로그인 유도
        }
    }

    // 서명을 검증하고 토큰 안의 정보(Claims)를 꺼냄. 검증 실패 시 JwtException 발생
    private Claims parseClaims(String token) {
        return Jwts.parser()
            .verifyWith(key)                     // 우리 비밀 키로 서명이 맞는지 확인
            .build()
            .parseSignedClaims(token)
            .getPayload();
    }
}
```

### auth/JwtAuthFilter.java

> 🤔 **왜 `OncePerRequestFilter`를 상속한 필터를 만드나요?**
> 컨트롤러에 도달하기 전에 "이 요청에 유효한 토큰이 있나?"를 매 요청마다 검사해야 한다. 필터는 컨트롤러보다 앞단에서 모든 요청을 가로채는 자리다. `OncePerRequestFilter`는 한 요청당 정확히 한 번만 실행되도록 보장해 준다. 여기서 토큰을 꺼내 검증하고, 통과하면 "이 사람은 userId N번"이라는 인증 정보(`SecurityContextHolder`)를 심어 둔다 → 이후 컨트롤러가 `Authentication`으로 그 사람을 알 수 있다.
>
> 🤔 **왜 토큰을 헤더와 쿠키 둘 다에서 찾나요?**
> 브라우저(React)는 토큰을 HttpOnly 쿠키에 담아 자동 전송하지만, Postman이나 모바일 앱은 `Authorization: Bearer ...` 헤더로 보내는 게 편하다. 두 경로를 모두 받아 주면 테스트(헤더)와 실제 서비스(쿠키)를 같은 코드로 처리할 수 있다.

```java
package com.makeapp.backend.auth;

import com.makeapp.backend.exception.CustomException;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.Cookie;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import lombok.RequiredArgsConstructor;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;
import java.util.List;

@Component
@RequiredArgsConstructor                         // final 필드(jwtProvider)를 받는 생성자 자동 생성 → 의존성 주입
public class JwtAuthFilter extends OncePerRequestFilter {  // 요청 1건당 1번 실행되는 필터

    private final JwtProvider jwtProvider;

    // 모든 요청이 컨트롤러에 닿기 전에 여기를 거친다
    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        String token = resolveToken(request);    // 요청에서 토큰 꺼내기 (헤더 또는 쿠키)
        if (token != null) {
            try {
                jwtProvider.validate(token);     // 토큰이 유효한지 검증 (만료/위조면 예외)
                if (jwtProvider.isGuest(token)) {
                    // 게스트 JWT: principal = participantId, 권한 = ROLE_GUEST
                    Long participantId = jwtProvider.getParticipantId(token);
                    var auth = new UsernamePasswordAuthenticationToken(
                            participantId, null,
                            List.of(new SimpleGrantedAuthority("ROLE_GUEST")));
                    SecurityContextHolder.getContext().setAuthentication(auth);  // "이 요청은 이 게스트"로 인증 등록
                } else {
                    // 소셜 로그인 JWT: principal = userId
                    Long userId = jwtProvider.getUserId(token);
                    var auth = new UsernamePasswordAuthenticationToken(userId, null, List.of());
                    SecurityContextHolder.getContext().setAuthentication(auth);  // 컨트롤러가 이 userId를 알게 됨
                }
            } catch (CustomException e) {
                // 만료/유효하지 않은 토큰 → 인증 없이 통과, Spring Security가 이후 401/403 처리
            }
        }
        filterChain.doFilter(request, response); // 다음 필터(최종적으로 컨트롤러)로 넘김
    }

    // 요청에서 토큰 문자열을 찾아 반환 (없으면 null)
    private String resolveToken(HttpServletRequest request) {
        // 1순위: Authorization 헤더 (Bearer 토큰 — Postman 테스트, 소셜 로그인)
        String bearer = request.getHeader("Authorization");
        if (bearer != null && bearer.startsWith("Bearer ")) {
            return bearer.substring(7);          // "Bearer " 7글자를 떼고 토큰만 반환
        }
        // 2순위: HttpOnly Cookie (브라우저가 자동으로 실어 보냄)
        if (request.getCookies() != null) {
            for (Cookie cookie : request.getCookies()) {
                if ("access_token".equals(cookie.getName())) {
                    return cookie.getValue();
                }
            }
        }
        return null;
    }
}
```

### config/SecurityConfig.java

> 🤔 **`SessionCreationPolicy.STATELESS`는 왜 쓰나요?**
> JWT를 쓰면 서버가 세션을 저장할 필요가 없다(증표는 토큰에 들어 있으니까). STATELESS는 "세션을 아예 만들지 마라"는 설정이다. 서버가 상태를 들고 있지 않으니 서버를 여러 대로 늘려도 어느 서버가 요청을 받든 토큰만 검증하면 된다(확장성).
>
> 🤔 **`csrf disable`은 보안을 끄는 거 아닌가요?**
> CSRF 공격은 "브라우저가 쿠키를 자동 전송한다"는 점을 악용하는데, 주로 세션 기반 인증에서 문제가 된다. 우리는 STATELESS + 토큰 기반이라 전통적인 CSRF 방어(세션 토큰)가 맞지 않아 끈다. 대신 쿠키에 `SameSite` 옵션(Phase 1-B 쿠키 설명 참고)으로 교차 사이트 전송을 제한한다.
>
> 🤔 **`addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)`는 왜 필요한가요?**
> Spring Security의 기본 필터 체인은 폼 로그인(아이디/비번)을 처리하는 `UsernamePasswordAuthenticationFilter`를 갖고 있다. 우리는 그 대신 JWT로 인증하므로, **그 필터보다 앞에** 우리 `JwtAuthFilter`를 끼워 넣어 토큰으로 먼저 인증을 끝낸다.
>
> <a id="phase1a-bcrypt"></a>🤔 **`BCryptPasswordEncoder`는 왜 쓰나요? (PIN/비밀번호 해시)**
> 게스트 PIN을 DB에 평문("1234")으로 저장하면 DB가 유출됐을 때 그대로 노출된다. BCrypt는 **단방향 해시**라 원문으로 되돌릴 수 없고, 매번 다른 salt를 섞어 같은 "1234"라도 저장값이 달라진다. 검증은 `matches(입력, 저장된해시)`로 한다(복호화가 아니라 다시 해시해서 비교). 그래서 Participant의 `pinHash`에 평문이 아닌 BCrypt 해시를 저장한다.
>
> 🤔 **`/api/auth/**`를 왜 `permitAll`로 여나요?**
> 로그인·회원가입 같은 엔드포인트는 *아직 토큰이 없는* 사용자가 호출한다. 여기까지 인증을 요구하면 로그인을 할 방법이 없다(닭과 달걀). 그래서 인증 엔드포인트와 공개 조회는 열어 두고, 나머지(`anyRequest().authenticated()`)는 토큰을 요구한다.

```java
package com.makeapp.backend.config;

import com.makeapp.backend.auth.JwtAuthFilter;
import lombok.RequiredArgsConstructor;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.config.annotation.web.configurers.AbstractHttpConfigurer;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.UsernamePasswordAuthenticationFilter;

import java.util.List;

@Configuration                                   // 스프링 설정 클래스
@EnableWebSecurity                               // Spring Security 활성화
@RequiredArgsConstructor
public class SecurityConfig {

    private final JwtAuthFilter jwtAuthFilter;   // 위에서 만든 JWT 인증 필터 주입

    @Bean                                        // PIN 해시용 인코더를 빈으로 등록 (다른 곳에서 주입받아 씀)
    public BCryptPasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean                                        // 보안 규칙 전체를 정의하는 필터 체인
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(AbstractHttpConfigurer::disable)  // 토큰 기반이라 세션 CSRF 방어 불필요 → 끔
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))  // 서버 세션 안 만듦
            .cors(cors -> cors.configurationSource(request -> {   // 프론트(다른 포트)에서의 요청 허용 설정
                var config = new org.springframework.web.cors.CorsConfiguration();
                config.setAllowedOrigins(List.of("http://localhost:5173"));   // 허용할 프론트 주소
                config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
                config.setAllowedHeaders(List.of("*"));
                config.setAllowCredentials(true);   // HttpOnly Cookie 전송에 필수
                return config;
            }))
            .authorizeHttpRequests(auth -> auth     // URL별 접근 권한 규칙 (위에서부터 순서대로 매칭)
                .requestMatchers("/api/auth/**").permitAll()   // 로그인 전 호출 → 인증 없이 허용 (guest 포함)
                .requestMatchers(HttpMethod.GET, "/api/meetings/**").permitAll()  // 모임 조회는 공개
                .requestMatchers(HttpMethod.POST, "/api/meetings/*/participants").permitAll()  // 참가 진입 허용
                .anyRequest().authenticated()       // 그 외 모든 요청은 토큰(인증) 필요
            )
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);  // 기본 로그인 필터 앞에 우리 필터 끼움

        return http.build();
    }
}
```

### dto/request/KakaoCallbackRequest.java

> 🤔 **왜 엔티티를 그대로 안 쓰고 요청용 DTO를 따로 만드나요?**
> 엔티티(User, Meeting...)는 DB 테이블과 1:1로 묶인 내부 모델이다. 이걸 API 입출력에 그대로 쓰면 (1) 클라이언트가 보내면 안 되는 필드까지 열리고, (2) 테이블 구조가 바뀌면 API가 깨지고, (3) 입력 검증 규칙을 붙이기 애매하다. 그래서 **요청 받는 모양은 Request DTO, 응답 주는 모양은 Response DTO**로 분리해 API의 입출력 경계를 명확히 한다.
>
> 🤔 **`@NotBlank` 같은 검증 애너테이션은 어떻게 동작하나요?**
> 컨트롤러에서 `@Valid`를 붙이면, 요청 본문이 객체로 변환될 때 이 규칙들이 자동 검사된다. 위반하면 컨트롤러 코드에 들어오기도 전에 예외가 발생하고, Phase 0의 `GlobalExceptionHandler`가 `400 INVALID_REQUEST`로 변환해 준다. 덕분에 서비스 로직은 "값은 일단 들어왔다"를 전제로 깔끔하게 짤 수 있다.

```java
package com.makeapp.backend.dto.request;

@Getter
```

### service/AuthService.java (생성)

이 단계에서는 `kakaoLogin`과 private 헬퍼만 작성한다. 이후 스텝에서 메서드를 추가해 나간다.

> 🤔 **Controller와 Service는 왜 나누나요? 그냥 컨트롤러에 다 짜면 안 되나요?**
> **컨트롤러**는 "HTTP 담당"이다 — 요청을 받고(`@RequestBody`), 검증하고(`@Valid`), 결과를 상태코드·쿠키로 포장해 응답한다. **서비스**는 "비즈니스 로직 담당"이다 — 카카오에 토큰을 요청하고, 사용자를 찾거나 만들고, JWT를 발급한다. 둘을 나누면 로직을 HTTP와 떼어 재사용·테스트하기 쉽고, 컨트롤러는 얇게 유지된다. 이번 기능을 세로로 관통하니 둘을 같이 만든다.
>
> 🤔 **클래스에 붙은 `@Transactional`은 무슨 의미인가요?**
> 서비스 메서드 하나를 **하나의 DB 트랜잭션**으로 묶는다. 메서드 중간에 예외가 나면 그 안에서 한 DB 변경이 전부 롤백된다(예: 사용자 저장 후 다른 작업이 실패하면 저장도 취소). 클래스에 붙이면 모든 public 메서드에 적용된다. 또 트랜잭션이 살아 있는 동안 LAZY 연관도 추가 조회할 수 있다.
>
> 🤔 **`findByKakaoId(...).orElseGet(() -> save(...))` 패턴은 뭔가요? (upsert)**
> 카카오 로그인은 회원가입과 로그인이 한 흐름이다. kakaoId로 기존 사용자를 찾되, **없으면(최초 로그인) 그 자리에서 새로 저장**한다. 즉 "있으면 로그인, 없으면 가입"을 한 줄로 처리한다. `orElseGet`은 값이 없을 때만 람다를 실행하므로, 기존 사용자가 있으면 불필요한 저장을 하지 않는다.
>
> 🤔 **외부 카카오 API는 왜 `RestClient`로 호출하나요?**
> 우리 서버가 카카오 서버에 "이 인가 코드의 사용자 정보 줘"라고 요청해야 한다(서버 간 통신). `RestClient`는 Spring이 제공하는 HTTP 클라이언트로, 외부 REST API를 동기 호출할 때 쓴다.

> ⚠️ **순서 주의:** 이 서비스 코드에는 `meetingRepository`/`participantRepository` 같은 필드가 아직 없다. 그건 게스트 기능(1-E)에서 추가하니, 지금은 아래 코드 그대로(회원 로그인에 필요한 것만) 작성하면 된다.

```java
package com.makeapp.backend.service;

import com.makeapp.backend.auth.JwtProvider;
import com.makeapp.backend.dto.response.AuthResponse;
import com.makeapp.backend.entity.User;
import com.makeapp.backend.exception.CustomException;
import com.makeapp.backend.exception.ErrorCode;
import com.makeapp.backend.repository.UserRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.http.MediaType;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.util.LinkedMultiValueMap;
import org.springframework.util.MultiValueMap;
import org.springframework.web.client.RestClient;

import java.util.Map;

@Service
@RequiredArgsConstructor                         // final 필드들을 생성자로 자동 주입
@Transactional                                   // 메서드를 트랜잭션으로 묶음 (도중 예외 시 DB 롤백)
public class AuthService {

    private final UserRepository userRepository;
    private final JwtProvider jwtProvider;
    private final BCryptPasswordEncoder passwordEncoder;

    @Value("${kakao.client-id}")                 // application.yaml의 kakao.client-id 값 주입
    private String kakaoClientId;

    @Value("${kakao.redirect-uri}")
    private String kakaoRedirectUri;

    private final RestClient restClient = RestClient.create();  // 외부(카카오) API 호출용 HTTP 클라이언트

    // 카카오 로그인 핵심 흐름: 인가코드 → 카카오 토큰 → 사용자정보 → 우리 회원 처리 → 우리 JWT 발급
    public AuthResponse kakaoLogin(String code) {
        String kakaoAccessToken = getKakaoAccessToken(code);          // 1) 인가코드로 카카오 토큰 받기
        Map<String, Object> kakaoUser = getKakaoUserInfo(kakaoAccessToken);  // 2) 토큰으로 사용자 정보 받기

        String kakaoId = String.valueOf(kakaoUser.get("id"));        // 카카오 고유 ID
        String name = extractNickname(kakaoUser);                    // 닉네임 추출

        // 3) 기존 회원이면 조회, 처음이면 가입(저장) → "있으면 로그인, 없으면 회원가입"
        User user = userRepository.findByKakaoId(kakaoId)
                .orElseGet(() -> userRepository.save(
                        User.builder().kakaoId(kakaoId).name(name).build()));
        user.updateName(name);                                       // 카카오에서 바뀐 이름 반영

        // 4) 우리 서비스용 access/refresh JWT 발급해서 반환
        return new AuthResponse(
                jwtProvider.createAccessToken(user.getId()),
                jwtProvider.createRefreshToken(user.getId()),
                new AuthResponse.UserInfo(user.getId(), user.getName()));
    }

    // 인가 코드를 카카오 토큰 발급 API에 보내 access_token을 받아옴
    @SuppressWarnings("unchecked")
    private String getKakaoAccessToken(String code) {
        try {
            // 카카오가 요구하는 폼 형식 파라미터 구성
            MultiValueMap<String, String> params = new LinkedMultiValueMap<>();
            params.add("grant_type", "authorization_code");
            params.add("client_id", kakaoClientId);
            params.add("redirect_uri", kakaoRedirectUri);
            params.add("code", code);

            Map<String, Object> response = restClient.post()
                    .uri("https://kauth.kakao.com/oauth/token")
                    .contentType(MediaType.APPLICATION_FORM_URLENCODED)
                    .body(params)
                    .retrieve()
                    .body(Map.class);

            return (String) response.get("access_token");
        } catch (Exception e) {
            throw new CustomException(ErrorCode.KAKAO_AUTH_FAILED);   // 실패 시 401로 변환
        }
    }

    // 카카오 access_token으로 사용자 정보 API 호출
    @SuppressWarnings("unchecked")
    private Map<String, Object> getKakaoUserInfo(String kakaoAccessToken) {
        try {
            return restClient.get()
                    .uri("https://kapi.kakao.com/v2/user/me")
                    .header("Authorization", "Bearer " + kakaoAccessToken)  // 받은 카카오 토큰을 헤더로 전달
                    .retrieve()
                    .body(Map.class);
        } catch (Exception e) {
            throw new CustomException(ErrorCode.KAKAO_AUTH_FAILED);
        }
    }

    // 카카오 응답 JSON에서 닉네임만 꺼냄 (중첩 구조라 단계별로 null 체크). 없으면 "사용자"
    @SuppressWarnings("unchecked")
    private String extractNickname(Map<String, Object> kakaoUser) {
        Map<String, Object> account = (Map<String, Object>) kakaoUser.get("kakao_account");
        if (account != null) {
            Map<String, Object> profile = (Map<String, Object>) account.get("profile");
            if (profile != null) return (String) profile.get("nickname");
        }
        return "사용자";
    }
}
```

### controller/AuthController.java (생성)

이 단계에서는 `kakaoCallback`과 `addCookie` 헬퍼만 작성한다. 이후 스텝에서 메서드를 추가해 나간다.

> <a id="phase1b-cookie"></a>🤔 **왜 토큰을 응답 본문이 아니라 HttpOnly 쿠키에 담나요? localStorage는 왜 안 되나요?**
> 토큰을 JS가 읽을 수 있는 곳(localStorage, 일반 쿠키)에 두면, **XSS 공격**으로 악성 스크립트가 토큰을 훔쳐 갈 수 있다. `httpOnly(true)` 쿠키는 **JS에서 접근이 불가능**하고 브라우저가 요청에 자동으로 실어 보내므로, 탈취 위험을 크게 줄인다. 그래서 브라우저용 토큰은 HttpOnly 쿠키로 내려보낸다.
> - `sameSite("Lax")`: 다른 사이트에서 우리 서버로의 요청에 쿠키가 함부로 실리지 않게 해 CSRF 위험을 줄인다.
> - `path("/")`: 모든 경로 요청에 쿠키가 따라가게 한다.
> - `maxAge`: 쿠키 수명(초). access는 3600(1시간), refresh는 604800(7일).
>
> 🤔 **서비스가 토큰을 반환했는데, 쿠키 세팅은 왜 컨트롤러가 하나요?**
> 쿠키는 HTTP 응답에 헤더를 다는 일이라 "HTTP 담당"인 컨트롤러의 몫이다. 서비스는 토큰 값(`AuthResponse`)만 만들어 주고, 컨트롤러가 그걸 받아 쿠키로 포장하고 상태코드를 정한다. 책임이 깔끔하게 나뉜다.
>
> 🤔 **로그인은 `200 OK`인데 게스트 등록은 왜 `201 Created`인가요?**
> HTTP 상태코드는 결과의 의미를 알려 준다. `200 OK`는 "요청 처리 성공", `201 Created`는 "성공했고 **새 리소스가 만들어졌다**"는 뜻이다. 게스트 등록(1-E)은 참가자를 새로 생성하므로 201이 더 정확하다.

```text
(아래는 1-B 시점의 AuthController다. refresh/logout/guest 메서드와 그에 필요한 import는
 1-C~1-F에서 하나씩 추가하니, 지금은 kakaoCallback + addCookie까지만 작성한다.)
```

```java
package com.makeapp.backend.controller;

import com.makeapp.backend.auth.JwtProvider;
import com.makeapp.backend.common.ApiResponse;
import com.makeapp.backend.dto.request.KakaoCallbackRequest;
import com.makeapp.backend.dto.response.AuthResponse;
import com.makeapp.backend.service.AuthService;
import jakarta.servlet.http.HttpServletResponse;
import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpHeaders;
import org.springframework.http.ResponseCookie;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/auth")
@RequiredArgsConstructor
public class AuthController {

    private final AuthService authService;
    private final JwtProvider jwtProvider;

    @PostMapping("/kakao/callback")              // POST /api/auth/kakao/callback
    public ResponseEntity<ApiResponse<AuthResponse>> kakaoCallback(
            @RequestBody @Valid KakaoCallbackRequest request,  // 요청 본문을 객체로 변환 + @Valid 검증
            HttpServletResponse response) {                    // 응답에 쿠키를 달기 위해 받음
        AuthResponse authResponse = authService.kakaoLogin(request.getCode());  // 로그인 로직은 서비스에 위임
        addCookie(response, "access_token", authResponse.getAccessToken(), 3600);        // 1시간짜리 쿠키
        addCookie(response, "refresh_token", authResponse.getRefreshToken(), 604800);    // 7일짜리 쿠키
        return ResponseEntity.ok(ApiResponse.ok(authResponse));                 // 200 OK + 통일된 응답 포맷
    }

    // 토큰을 HttpOnly 쿠키로 만들어 응답 헤더에 추가하는 공통 헬퍼
    private void addCookie(HttpServletResponse response, String name, String token, long maxAge) {
        ResponseCookie cookie = ResponseCookie.from(name, token)
                .httpOnly(true)                  // JS에서 접근 불가 (XSS로부터 토큰 보호)
                .path("/")                       // 모든 경로 요청에 쿠키 전송
                .sameSite("Lax")                 // 교차 사이트 요청에 쿠키 제한 (CSRF 완화)
                .maxAge(maxAge)                  // 쿠키 수명(초). 0이면 즉시 삭제
                .build();
        response.addHeader(HttpHeaders.SET_COOKIE, cookie.toString());
    }
}
```

## Phase 1-C — 토큰 갱신  `POST /api/auth/refresh`

refresh_token 쿠키를 읽어 새 access_token을 발급한다.

> 🤔 **access_token이 있는데 refresh_token은 왜 따로 있나요?**
> access_token은 수명이 짧다(1시간). 짧을수록 탈취돼도 피해가 적기 때문이다. 하지만 1시간마다 다시 로그인하면 불편하다. 그래서 수명이 긴 refresh_token(7일)을 따로 두고, access가 만료되면 **refresh로 새 access를 조용히 재발급**한다. 사용자는 7일 동안 재로그인 없이 쓸 수 있다.
>
> 🤔 **refresh_token을 요청 본문이 아니라 쿠키에서 읽는 이유는?**
> refresh_token도 HttpOnly 쿠키로 관리하므로 JS가 못 읽는다(보안). 따라서 클라이언트가 본문에 담아 보낼 수 없고, 브라우저가 자동 전송한 쿠키에서 서버가 직접 꺼내야 한다. 그래서 이 API는 요청 본문이 비어 있다.

### AuthService.java에 추가

```java
// refresh token이 유효하면, 그 안의 userId로 새 access token을 발급
public String refreshAccessToken(String refreshToken) {
    if (!jwtProvider.isValid(refreshToken)) {            // 만료/위조된 refresh면 거부
        throw new CustomException(ErrorCode.INVALID_TOKEN);
    }
    return jwtProvider.createAccessToken(jwtProvider.getUserId(refreshToken));
}
```

## Phase 1-E — 게스트 등록  `POST /api/auth/guest/register`

비회원이 초대 링크를 통해 처음 참가할 때 닉네임과 PIN을 등록하고 게스트 JWT를 발급받는다.

> ⚠️ **이 단계는 코드만 작성하고, Postman 테스트는 Phase 2(모임 생성)로 `INVITE_TOKEN`을 얻은 뒤에 한다.** (위 Phase 1 도입부 의존성 안내 참고.)
>
> 🤔 **게스트는 왜 카카오 없이 닉네임+PIN으로 인증하나요?**
> 모임에 참가하는 사람 모두에게 카카오 가입을 요구하면 진입 장벽이 높다. 그래서 비회원은 초대 링크로 들어와 "닉네임 + 4자리 PIN"만으로 참가한다. PIN은 다른 기기에서 재접속(1-F)할 때 본인 확인용이다. PIN은 평문이 아니라 BCrypt 해시로 저장한다(Phase 1-A BCrypt 설명 참고).
>
> 🤔 **게스트 토큰은 일반 회원 토큰과 뭐가 다른가요?**
> 게스트는 User 테이블에 없고 특정 모임의 Participant로만 존재한다. 그래서 `createGuestToken`은 subject에 userId 대신 **participantId**를 담고, claim에 `meetingId`와 `role="GUEST"`를 추가한다. 필터(`JwtAuthFilter`)는 이 `role`을 보고 게스트인지 회원인지 구분해 인증 주체를 다르게 세팅한다 → 게스트는 자기 모임 범위에서만 활동하게 된다.
>
> 🤔 **`resolveDisplayName`으로 중복 닉네임을 왜 처리하나요?**
> 한 모임에 "철수"가 둘일 수 있다. 닉네임이 겹치면 1-F 로그인 때 누가 누구인지 못 가린다. 그래서 같은 모임에 같은 이름이 이미 있으면 "철수 (2)"처럼 뒤에 번호를 붙여 모임 안에서 닉네임이 유일하도록 만든다.

```java
public Participant guestRegister(String inviteToken, String displayName, String rawPin) {
    Meeting meeting = meetingRepository.findByInviteToken(inviteToken)
            .orElseThrow(() -> new CustomException(ErrorCode.MEETING_NOT_FOUND));  // 모임 없으면 404
    if (meeting.getStatus() == MeetingStatus.EXPIRED) {
        throw new CustomException(ErrorCode.MEETING_EXPIRED);                      // 만료된 모임은 참가 불가
    }
    if (displayName == null || displayName.isBlank()) {
        throw new CustomException(ErrorCode.INVALID_REQUEST);
    }
    String pinHash = passwordEncoder.encode(rawPin);                  // PIN을 BCrypt 해시로 변환(평문 저장 X)
    String resolvedName = resolveDisplayName(meeting, displayName);   // 중복 이름이면 "(2)" 붙여 유일하게
    return participantRepository.save(Participant.builder()
            .meeting(meeting)
            .pinHash(pinHash)
            .displayName(resolvedName)
            .type(ParticipantType.GUEST)
            .build());
}

private String resolveDisplayName(Meeting meeting, String baseName) {
    long count = participantRepository.findByMeeting(meeting).stream()
            .filter(p -> p.getDisplayName().equals(baseName)
                    || p.getDisplayName().startsWith(baseName + " ("))   // "철수", "철수 (2)" 등을 셈
            .count();
    return count == 0 ? baseName : baseName + " (" + (count + 1) + ")";
}
```

## Phase 1-F — 게스트 로그인  `POST /api/auth/guest/login`

기존 게스트 참가자가 다른 기기에서 재접속할 때 닉네임 + PIN으로 인증하고 게스트 JWT를 재발급받는다.

> ⚠️ **이 단계도 코드만 작성하고, Postman 테스트는 Phase 2 이후에 한다.**
>
> 🤔 **PIN을 `passwordEncoder.matches()`로 검증하는데, 왜 5회 실패 시 잠그나요?**
> PIN은 0000~9999, 1만 가지뿐이라 무차별 대입(brute force)에 약하다. 누군가 PIN을 계속 찍어 남의 참가 정보를 가로채는 걸 막으려고, 5회 연속 틀리면 30분간 잠근다(`incrementPinFail`/`isPinLocked`). 성공하면 실패 카운트를 초기화(`resetPinFail`)한다. 이 잠금 규칙은 Participant 엔티티가 직접 들고 있어(도메인 응집) 서비스는 호출만 한다.
>
> 🤔 **GuestRegisterRequest와 GuestLoginRequest는 거의 같은데 왜 따로 두나요?**
> 지금은 필드가 비슷하지만 **의미와 검증 규칙이 다르다.** 등록은 새 닉네임을 만드는 것이라 `displayName`에 `@Size(max=50)` 제한이 필요하고, 로그인은 *이미 존재하는* 닉네임을 찾는 것이라 길이 제한이 의미 없다. 또 두 기능은 앞으로 다른 방향으로 바뀔 가능성이 크다(예: 등록에 약관 동의 추가). 억지로 합치면 한쪽 변경이 다른 쪽을 깨뜨린다. 그래서 입력의 "용도"가 다르면 DTO를 나눈다.

```java
// 게스트 재로그인: 모임+닉네임으로 기존 참가자를 찾아 PIN을 검증
public Participant guestLogin(String inviteToken, String displayName, String rawPin) {
    Meeting meeting = meetingRepository.findByInviteToken(inviteToken)
            .orElseThrow(() -> new CustomException(ErrorCode.MEETING_NOT_FOUND));
    Participant p = participantRepository.findByMeetingAndDisplayName(meeting, displayName)
            .orElseThrow(() -> new CustomException(ErrorCode.GUEST_NOT_FOUND));  // 그 이름의 게스트 없으면 404

    if (p.isPinLocked()) {
        throw new CustomException(ErrorCode.PIN_LOCKED);                         // 잠겨 있으면 429
    }
    if (!passwordEncoder.matches(rawPin, p.getPinHash())) {   // 입력 PIN을 해시와 비교 (복호화가 아님)
        p.incrementPinFail();                                // 틀리면 실패 횟수 +1 (5회 시 잠금)
        throw new CustomException(ErrorCode.PIN_MISMATCH);
    }
    p.resetPinFail();                                        // 성공하면 실패 기록 초기화
    return p;
}
```

```java
            this.slotDate = slot.getSlotDate();

            this.endTime = slot.getEndTime();
```

## service/MeetingService.java (생성)

이 단계에서는 `create`만 작성한다. 이후 Phase에서 메서드를 추가해 나간다.

> 🤔 **invite_token과 result_token을 왜 둘 다, 그것도 UUID로 만드나요?**
> 모임 링크는 로그인 없이 누구나 열 수 있어야 해서 **추측 불가능한 임의 문자열**이 필요하다. `id=1, 2, 3`처럼 순번이면 남의 모임을 쉽게 넘겨볼 수 있다. UUID는 사실상 겹치지도 추측되지도 않는다. 또 **권한을 분리**하려고 토큰을 둘로 나눈다 — `invite_token`은 "참가용"(참가자에게 공유), `result_token`은 "결과 확인용"(다른 권한/용도). 하나가 유출돼도 다른 기능은 보호된다.

> 🤔 **`@Transactional(readOnly = true)`는 Phase 3에서 나오는데 뭐가 다른가요?**
> 조회만 하는 메서드에 `readOnly = true`를 붙이면, JPA가 "이 트랜잭션은 데이터를 안 바꾼다"고 알고 변경 감지(dirty checking) 등을 생략해 약간 더 가볍게 동작하고, 의도("이건 읽기 전용")도 코드에 드러난다. 생성/수정 메서드(`create` 등)는 데이터를 바꾸므로 일반 `@Transactional`을 쓴다.

```java
package com.makeapp.backend.service;

import com.makeapp.backend.dto.request.MeetingCreateRequest;
import com.makeapp.backend.dto.response.MeetingResponse;
import com.makeapp.backend.entity.*;
import com.makeapp.backend.exception.CustomException;
import com.makeapp.backend.exception.ErrorCode;
import com.makeapp.backend.repository.*;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.List;
import java.util.UUID;

@Service
@RequiredArgsConstructor
@Transactional
public class MeetingService {

    private static final String FRONT_BASE_URL = "http://localhost:5173";

    private final MeetingRepository meetingRepository;
    private final CandidateSlotRepository candidateSlotRepository;
    private final UserRepository userRepository;

    // 모임 생성: 로그인 사용자를 주최자로, 후보 슬롯들과 함께 저장
    public MeetingResponse create(Long userId, MeetingCreateRequest request) {
        User user = userRepository.findById(userId)
                .orElseThrow(() -> new CustomException(ErrorCode.UNAUTHORIZED));  // 토큰의 userId가 실제 회원인지 확인

        Meeting meeting = meetingRepository.save(Meeting.builder()
                .owner(user)
                .name(request.getName())
                .expectedCount(request.getExpectedCount())
                .inviteToken(UUID.randomUUID().toString())   // 추측 불가능한 초대 토큰 자동 생성
                .resultToken(UUID.randomUUID().toString())   // 결과 토큰도 별도 생성
                .build());

        // 요청의 후보 슬롯들을 각각 저장하고 리스트로 모음
        List<CandidateSlot> slots = request.getCandidateSlots().stream()
                .map(s -> candidateSlotRepository.save(CandidateSlot.builder()
                        .meeting(meeting)
                        .slotDate(s.getSlotDate())
                        .startTime(s.getStartTime())
                        .endTime(s.getEndTime())
                        .build()))
                .toList();

        return new MeetingResponse(meeting, slots, FRONT_BASE_URL);   // 저장 결과를 응답 DTO로 변환
    }
}
```

## controller/MeetingController.java (생성)

이 단계에서는 `create`와 `getLoginUserId` 헬퍼만 작성한다. 이후 Phase에서 메서드를 추가해 나간다.

> 🤔 **컨트롤러 파라미터의 `Authentication auth`는 어디서 오나요?**
> Phase 1-A의 `JwtAuthFilter`가 토큰을 검증한 뒤 `SecurityContextHolder`에 인증 정보를 심어 둔다. Spring Security가 그걸 컨트롤러 메서드의 `Authentication` 파라미터로 주입해 준다. 그래서 `auth.getPrincipal()`로 "지금 요청한 사람의 userId"를 꺼낼 수 있다. `getLoginUserId` 헬퍼는 인증이 없거나(`auth == null`) 비정상일 때 `UNAUTHORIZED`로 막아 주는 공통 처리다.

```java
package com.makeapp.backend.controller;

import com.makeapp.backend.common.ApiResponse;
import com.makeapp.backend.dto.request.MeetingCreateRequest;
import com.makeapp.backend.dto.response.MeetingResponse;
import com.makeapp.backend.exception.CustomException;
import com.makeapp.backend.exception.ErrorCode;
import com.makeapp.backend.service.MeetingService;
import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.security.core.Authentication;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/meetings")
@RequiredArgsConstructor
public class MeetingController {

    private final MeetingService meetingService;

    @PostMapping                                 // POST /api/meetings
    public ResponseEntity<ApiResponse<MeetingResponse>> create(
            @RequestBody @Valid MeetingCreateRequest request,
            Authentication auth) {               // 필터가 넣어준 인증 정보 (로그인한 사람)
        return ResponseEntity.status(HttpStatus.CREATED)   // 201 Created
                .body(ApiResponse.ok(meetingService.create(getLoginUserId(auth), request)));
    }

    // 인증 정보에서 userId를 꺼내는 공통 헬퍼 (없으면 401)
    private Long getLoginUserId(Authentication auth) {
        if (auth == null || !auth.isAuthenticated()) {
            throw new CustomException(ErrorCode.UNAUTHORIZED);
        }
        return (Long) auth.getPrincipal();       // 필터에서 principal에 userId를 넣어 둠
    }
}
```

## service/ParticipantService.java

> 🤔 **회원 참가는 왜 게스트(1-E)와 다른 엔드포인트로 나뉘나요?**
> 둘 다 "참가자(Participant)를 만든다"는 결과는 같지만 **인증 방식이 완전히 다르다.** 회원은 이미 JWT로 본인이 확인되므로 토큰의 userId만 보면 되고, 게스트는 토큰이 없어 닉네임+PIN으로 새로 신원을 만든다. 인증 흐름이 다르면 한 메서드에 `if 회원 / else 게스트`로 욱여넣기보다 엔드포인트를 나누는 편이 깔끔하다.
>
> 🤔 **`existsByMeetingAndUser`로 중복 참가를 막고, LEADER/MEMBER를 나누는 이유는?**
> 한 사람이 같은 모임에 여러 번 참가하면 집계가 꼬인다. 그래서 이미 참가 중이면 `DUPLICATE_PARTICIPATION`으로 막는다. 또 모임 생성자(owner)가 참가하면 `LEADER`, 나머지 회원은 `MEMBER`로 역할을 구분해 둔다 — 나중에 확정/삭제 같은 권한 있는 동작(Phase 7)을 누가 할 수 있는지 가리는 데 쓰인다.

```java
package com.makeapp.backend.service;

import com.makeapp.backend.dto.request.ParticipantJoinRequest;
import com.makeapp.backend.dto.response.ParticipantResponse;
import com.makeapp.backend.entity.*;
import com.makeapp.backend.exception.CustomException;
import com.makeapp.backend.exception.ErrorCode;
import com.makeapp.backend.repository.*;
import lombok.RequiredArgsConstructor;
import org.springframework.security.core.Authentication;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.List;

@Service
@RequiredArgsConstructor
@Transactional
public class ParticipantService {

    private final MeetingRepository meetingRepository;
    private final ParticipantRepository participantRepository;
    private final UserRepository userRepository;

    // 소셜 로그인 회원만 이 엔드포인트로 참가. 게스트는 /api/auth/guest/register 사용.
    public ParticipantResponse join(String inviteToken, ParticipantJoinRequest request, Long userId) {
        Meeting meeting = meetingRepository.findByInviteToken(inviteToken)
                .orElseThrow(() -> new CustomException(ErrorCode.MEETING_NOT_FOUND));
        if (meeting.getStatus() == MeetingStatus.EXPIRED) {
            throw new CustomException(ErrorCode.MEETING_EXPIRED);      // 만료된 모임엔 참가 불가
        }
        if (userId == null) throw new CustomException(ErrorCode.UNAUTHORIZED);  // 로그인 안 했으면 거부

        User user = userRepository.findById(userId)
                .orElseThrow(() -> new CustomException(ErrorCode.UNAUTHORIZED));
        if (participantRepository.existsByMeetingAndUser(meeting, user)) {
            throw new CustomException(ErrorCode.DUPLICATE_PARTICIPATION);  // 이미 참가했으면 중복 차단
        }
        boolean isOwner = meeting.getOwner().getId().equals(userId);  // 주최자가 직접 참가하는 경우
        Participant p = participantRepository.save(Participant.builder()
                .meeting(meeting)
                .user(user)
                .displayName(resolveDisplayName(meeting, user.getName()))   // 이름 중복 시 "(n)" 처리
                .type(isOwner ? ParticipantType.LEADER : ParticipantType.MEMBER)  // 주최자=LEADER, 그 외=MEMBER
                .build());
        return ParticipantResponse.of(p);
    }

    // 같은 모임 내 이름 중복 방지 ("철수" → "철수 (2)")  ※ 게스트 등록의 같은 로직과 동일
    private String resolveDisplayName(Meeting meeting, String baseName) {
        long count = participantRepository.findByMeeting(meeting).stream()
                .filter(p -> p.getDisplayName().equals(baseName)
                        || p.getDisplayName().startsWith(baseName + " ("))
                .count();
        return count == 0 ? baseName : baseName + " (" + (count + 1) + ")";
    }

    // 모임의 참가자 전체 목록 조회 (각 참가자 → 응답 DTO)
    @Transactional(readOnly = true)
    public List<ParticipantResponse> findAll(String inviteToken) {
        Meeting meeting = meetingRepository.findByInviteToken(inviteToken)
                .orElseThrow(() -> new CustomException(ErrorCode.MEETING_NOT_FOUND));
        return participantRepository.findByMeeting(meeting).stream()
                .map(ParticipantResponse::of).toList();
    }

    // "내 참가 정보" 조회: 토큰이 게스트냐 회원이냐에 따라 찾는 방법이 다름
    @Transactional(readOnly = true)
    public ParticipantResponse findMe(String inviteToken, Authentication auth) {
        Meeting meeting = meetingRepository.findByInviteToken(inviteToken)
                .orElseThrow(() -> new CustomException(ErrorCode.MEETING_NOT_FOUND));
        if (auth == null) throw new CustomException(ErrorCode.UNAUTHORIZED);

        // 권한 목록에 ROLE_GUEST가 있으면 게스트 토큰
        boolean isGuest = auth.getAuthorities().stream()
                .anyMatch(a -> a.getAuthority().equals("ROLE_GUEST"));

        if (isGuest) {
            Long participantId = (Long) auth.getPrincipal();   // 게스트는 principal이 participantId
            return participantRepository.findById(participantId)
                    .filter(p -> p.getMeeting().getId().equals(meeting.getId()))  // 이 모임 소속인지 확인
                    .map(ParticipantResponse::of)
                    .orElseThrow(() -> new CustomException(ErrorCode.PARTICIPANT_NOT_FOUND));
        }

        Long userId = (Long) auth.getPrincipal();              // 회원은 principal이 userId
        User user = userRepository.findById(userId)
                .orElseThrow(() -> new CustomException(ErrorCode.UNAUTHORIZED));
        return participantRepository.findByMeetingAndUser(meeting, user)
                .map(ParticipantResponse::of)
                .orElseThrow(() -> new CustomException(ErrorCode.PARTICIPANT_NOT_FOUND));
    }
}
```

## dto/request/AvailabilitySubmitRequest.java

## service/AvailabilityService.java

> 🤔 **왜 "추가(insert)"가 아니라 `upsert`(있으면 수정, 없으면 생성)인가요?**
> 사용자는 가용 시간을 한 번 내고 끝내지 않고 **여러 번 고친다.** 매번 새로 insert하면 같은 슬롯에 대한 응답이 중복으로 쌓인다. 그래서 `findByParticipantAndCandidateSlot`으로 기존 응답을 찾아 **있으면 상태만 갱신, 없으면 새로 생성**한다(`orElseGet`). 이렇게 "한 참가자–한 슬롯 = 한 행"을 유지하는 게 upsert다.
>
> 🤔 **`resolveParticipant`에서 회원/게스트를 또 나누는 이유는?**
> 가용 시간을 내는 주체가 회원일 수도, 게스트일 수도 있다. 토큰의 권한(`ROLE_GUEST`)을 보고 게스트면 participantId로, 회원이면 userId→Participant로 찾아 **둘 다 "이 모임의 참가자"로 환원**한다. 이후 로직은 참가자 한 명만 다루면 되므로 단순해진다.

```java
package com.makeapp.backend.service;

import com.makeapp.backend.dto.request.AvailabilitySubmitRequest;
import com.makeapp.backend.entity.*;
import com.makeapp.backend.exception.CustomException;
import com.makeapp.backend.exception.ErrorCode;
import com.makeapp.backend.repository.*;
import lombok.RequiredArgsConstructor;
import org.springframework.security.core.Authentication;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.*;

@Service
@RequiredArgsConstructor
@Transactional
public class AvailabilityService {

    private final MeetingRepository meetingRepository;
    private final ParticipantRepository participantRepository;
    private final CandidateSlotRepository candidateSlotRepository;
    private final AvailabilityRepository availabilityRepository;
    private final UserRepository userRepository;

    // 가용 시간 제출/수정: 슬롯마다 응답을 저장하되, 이미 있으면 갱신 (UPSERT)
    public Map<String, Integer> upsert(String inviteToken,
                                       AvailabilitySubmitRequest request,
                                       Authentication auth) {
        Participant participant = resolveParticipant(inviteToken, auth);  // 요청자를 이 모임의 참가자로 환원
        int count = 0;
        for (var item : request.getAvailabilities()) {       // 받은 응답들을 하나씩 처리
            CandidateSlot slot = candidateSlotRepository.findById(item.getCandidateSlotId())
                    .orElseThrow(() -> new CustomException(ErrorCode.INVALID_SLOT));  // 없는 슬롯이면 거부
            AvailabilityStatus status = AvailabilityStatus.valueOf(item.getStatus());  // 문자열 → enum

            // 기존 응답이 있으면 그것을, 없으면 새 객체를 만든다 (UPSERT의 핵심)
            Availability avail = availabilityRepository
                    .findByParticipantAndCandidateSlot(participant, slot)
                    .orElseGet(() -> Availability.builder()
                            .participant(participant).candidateSlot(slot).status(status).build());
            avail.updateStatus(status);                      // 상태 갱신
            availabilityRepository.save(avail);
            count++;
        }
        return Map.of("updatedCount", count);                // 처리한 개수 반환
    }

    // 제출 완료 처리: 참가자에 제출 시각을 찍음
    public Map<String, String> submit(String inviteToken, Authentication auth) {
        Participant participant = resolveParticipant(inviteToken, auth);
        participant.submit();
        return Map.of("submittedAt", participant.getSubmittedAt().toString());
    }

    // 슬롯별 현황 조회: 각 후보 시간마다 가능/불가능 참가자 이름 목록을 만든다
    @Transactional(readOnly = true)
    public List<Map<String, Object>> getAvailabilities(String inviteToken) {
        Meeting meeting = meetingRepository.findByInviteToken(inviteToken)
                .orElseThrow(() -> new CustomException(ErrorCode.MEETING_NOT_FOUND));
        return candidateSlotRepository.findByMeeting(meeting).stream().map(slot -> {
            List<Availability> avails = availabilityRepository.findByCandidateSlot(slot);  // 이 슬롯의 모든 응답
            Map<String, Object> r = new LinkedHashMap<>();   // 순서 유지되는 Map (응답 키 순서대로)
            r.put("candidateSlotId", slot.getId());
            r.put("slotDate", slot.getSlotDate().toString());
            r.put("startTime", slot.getStartTime().toString());
            r.put("endTime", slot.getEndTime().toString());
            r.put("availableParticipants", avails.stream()   // 가능하다고 한 사람들의 이름
                    .filter(a -> a.getStatus() == AvailabilityStatus.AVAILABLE)
                    .map(a -> a.getParticipant().getDisplayName()).toList());
            r.put("unavailableParticipants", avails.stream() // 불가능하다고 한 사람들의 이름
                    .filter(a -> a.getStatus() == AvailabilityStatus.UNAVAILABLE)
                    .map(a -> a.getParticipant().getDisplayName()).toList());
            return r;
        }).toList();
    }

    // 요청자(회원/게스트)를 "이 모임의 참가자"로 찾아 반환하는 공통 헬퍼
    private Participant resolveParticipant(String inviteToken, Authentication auth) {
        Meeting meeting = meetingRepository.findByInviteToken(inviteToken)
                .orElseThrow(() -> new CustomException(ErrorCode.MEETING_NOT_FOUND));
        if (auth == null) throw new CustomException(ErrorCode.UNAUTHORIZED);

        boolean isGuest = auth.getAuthorities().stream()     // 게스트 토큰인지 확인
                .anyMatch(a -> a.getAuthority().equals("ROLE_GUEST"));

        if (isGuest) {
            Long participantId = (Long) auth.getPrincipal(); // 게스트: principal = participantId
            return participantRepository.findById(participantId)
                    .filter(p -> p.getMeeting().getId().equals(meeting.getId()))  // 이 모임 소속 확인
                    .orElseThrow(() -> new CustomException(ErrorCode.PARTICIPANT_NOT_FOUND));
        }

        Long userId = (Long) auth.getPrincipal();            // 회원: principal = userId
        User user = userRepository.findById(userId)
                .orElseThrow(() -> new CustomException(ErrorCode.UNAUTHORIZED));
        return participantRepository.findByMeetingAndUser(meeting, user)
                .orElseThrow(() -> new CustomException(ErrorCode.PARTICIPANT_NOT_FOUND));
    }
}
```

# Phase 6 — 결과 조회 + 추천

> **목표 API**: `GET /api/meetings/{inviteToken}/results?sort=recommend|date|duration`
> 인증 불필요. 슬롯별 가능 인원 집계 + 최적 추천 슬롯 표시.

## service/ResultService.java

> 🤔 **추천 슬롯(`isTopRecommendation`)은 어떤 기준으로 정하나요?**
> 목적은 "가장 많은 사람이 가능한 시간"을 찾는 것이다. 그래서 슬롯마다 AVAILABLE 응답 수를 세고, 그중 **최댓값(`maxAvailable`)과 같은 슬롯**에 `isTopRecommendation=true`를 단다(동점이면 여러 개일 수 있다). 정렬은 사용자가 고른 기준(`recommend`=가능 인원순, `date`=날짜순, `duration`=길이순)에 따라 `switch`로 비교자를 바꾼다.
>
> 🤔 **이 서비스는 왜 클래스 전체에 `@Transactional(readOnly = true)`를 붙였나요?**
> 결과 조회는 데이터를 전혀 바꾸지 않는 순수 조회 기능이다. 클래스에 한 번 붙여 두면 모든 메서드가 읽기 전용 트랜잭션으로 동작해 의도가 명확하고 약간 가볍다. (쓰기가 필요한 메서드가 생기면 그 메서드에만 `@Transactional`을 따로 붙여 덮어쓴다.)

```java
package com.makeapp.backend.service;

import com.makeapp.backend.entity.*;
import com.makeapp.backend.exception.CustomException;
import com.makeapp.backend.exception.ErrorCode;
import com.makeapp.backend.repository.*;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.Duration;
import java.util.*;

@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class ResultService {

    private final MeetingRepository meetingRepository;
    private final CandidateSlotRepository candidateSlotRepository;
    private final AvailabilityRepository availabilityRepository;
    private final ParticipantRepository participantRepository;

    // 결과 집계 + 추천: 슬롯마다 가능 인원을 세고, 가장 많은 슬롯을 추천으로 표시
    public Map<String, Object> getResults(String inviteToken, String sort) {
        Meeting meeting = meetingRepository.findByInviteToken(inviteToken)
                .orElseThrow(() -> new CustomException(ErrorCode.MEETING_NOT_FOUND));

        int total = participantRepository.findByMeeting(meeting).size();   // 전체 참가자 수
        List<CandidateSlot> slots = candidateSlotRepository.findByMeeting(meeting);

        // 슬롯마다 가능/불가능 인원, 소요시간 등을 계산해 Map으로 만듦
        List<Map<String, Object>> slotResults = slots.stream().map(slot -> {
            List<Availability> avails = availabilityRepository.findByCandidateSlot(slot);
            long available = avails.stream()
                    .filter(a -> a.getStatus() == AvailabilityStatus.AVAILABLE).count();   // 가능 인원
            long unavailable = avails.stream()
                    .filter(a -> a.getStatus() == AvailabilityStatus.UNAVAILABLE).count(); // 불가능 인원
            int duration = (int) Duration.between(slot.getStartTime(), slot.getEndTime()).toMinutes();  // 분 단위 길이

            Map<String, Object> r = new LinkedHashMap<>();
            r.put("candidateSlotId", slot.getId());
            r.put("slotDate", slot.getSlotDate().toString());
            r.put("startTime", slot.getStartTime().toString());
            r.put("endTime", slot.getEndTime().toString());
            r.put("availableCount", (int) available);
            r.put("unavailableCount", (int) unavailable);
            r.put("recommendationLabel", total + "명 중 " + available + "명 가능");
            r.put("durationMinutes", duration);
            return r;
        }).toList();

        // 가능 인원의 최댓값 (이 값과 같은 슬롯이 "추천")
        int maxAvailable = slotResults.stream()
                .mapToInt(r -> (int) r.get("availableCount")).max().orElse(0);

        List<Map<String, Object>> sorted = sortSlots(new ArrayList<>(slotResults), sort);  // 정렬
        // 가능 인원이 최댓값과 같은 슬롯에 추천 표시
        sorted.forEach(r -> r.put("isTopRecommendation", (int) r.get("availableCount") == maxAvailable));

        // 최종 응답 조립
        Map<String, Object> response = new LinkedHashMap<>();
        response.put("meetingId", meeting.getId());
        response.put("meetingName", meeting.getName());
        response.put("status", meeting.getStatus().name());
        response.put("totalParticipants", total);
        if (meeting.getConfirmedSlot() != null) {
            response.put("confirmedSlotId", meeting.getConfirmedSlot().getId());
        }
        response.put("slots", sorted);
        return response;
    }

    // 정렬 기준(sort 값)에 따라 슬롯 목록을 정렬
    private List<Map<String, Object>> sortSlots(List<Map<String, Object>> slots, String sort) {
        Comparator<Map<String, Object>> cmp = switch (sort != null ? sort : "recommend") {
            case "date" -> Comparator.comparing(r -> (String) r.get("slotDate"));   // 날짜 오름차순
            case "duration" -> Comparator.comparingInt(
                    (Map<String, Object> r) -> (int) r.get("durationMinutes")).reversed();  // 긴 시간 먼저
            default -> Comparator.comparingInt(
                    (Map<String, Object> r) -> (int) r.get("availableCount")).reversed();   // 가능 인원 많은 순(기본)
        };
        return slots.stream().sorted(cmp).toList();
    }
}
```

# Phase 7 — 모임 확정 / 만료 / 취소

> **목표 API**: `POST /api/meetings/{id}/confirm`, `POST /api/meetings/{id}/expire`, `POST /api/meetings/{id}/cancel`
> Bearer 인증 + 모임 생성자(LEADER) 권한 검증.

## MeetingService.java에 추가

> 🤔 **확정/만료/취소는 왜 `findAndCheckOwner`로 매번 소유자를 확인하나요?**
> 이 동작들은 모임에 영향을 주는 **민감한 권한 작업**이다. 아무 참가자나 남의 모임을 확정·삭제하면 안 된다. 그래서 공통 헬퍼에서 "모임 존재 확인 + 요청자가 owner인지 확인"을 함께 처리하고, 아니면 `FORBIDDEN`(403)으로 막는다. 세 메서드가 같은 검사를 반복하므로 헬퍼로 묶어 중복을 없앴다.
>
> 🤔 **취소(`cancel`)는 왜 진짜 삭제가 아니라 `delete()`(soft delete)인가요?**
> Phase 0에서 본 것처럼 `delete()`는 `deleted_at`만 채운다. 모임을 물리 삭제하면 거기에 달린 참가자·가용시간 데이터까지 한꺼번에 잃고 복구도 안 된다. soft delete면 `@SQLRestriction` 덕에 조회에서는 사라지지만 데이터는 남아 안전하다.

```java
// 모임 확정: 주최자만 가능, 이미 확정됐으면 거부, 지정한 슬롯으로 확정
public void confirm(Long meetingId, Long userId, Long confirmedSlotId) {
    Meeting meeting = findAndCheckOwner(meetingId, userId);   // 존재 + 주최자 확인
    if (meeting.getStatus() == MeetingStatus.CONFIRMED) {
        throw new CustomException(ErrorCode.MEETING_ALREADY_CONFIRMED);  // 중복 확정 방지
    }
    CandidateSlot slot = candidateSlotRepository.findById(confirmedSlotId)
            .orElseThrow(() -> new CustomException(ErrorCode.INVALID_SLOT));
    meeting.confirm(slot);                                    // 엔티티가 상태/확정슬롯 변경 (트랜잭션 끝에 자동 반영)
}

// 모임 만료: 주최자만 가능, 확정된 모임은 만료 불가
public void expire(Long meetingId, Long userId) {
    Meeting meeting = findAndCheckOwner(meetingId, userId);
    if (meeting.getStatus() == MeetingStatus.CONFIRMED) {
        throw new CustomException(ErrorCode.MEETING_ALREADY_CONFIRMED);
    }
    meeting.expire();
}

// 모임 삭제: 주최자만 가능, 물리 삭제 대신 Soft Delete
public void cancel(Long meetingId, Long userId) {
    findAndCheckOwner(meetingId, userId).delete();           // deleted_at만 기록 → 조회에서 사라짐
}

// "모임이 존재하고 + 요청자가 주최자인지" 검사하는 공통 헬퍼 (세 메서드가 공유)
private Meeting findAndCheckOwner(Long meetingId, Long userId) {
    Meeting meeting = meetingRepository.findById(meetingId)
            .orElseThrow(() -> new CustomException(ErrorCode.MEETING_NOT_FOUND));
    if (!meeting.getOwner().getId().equals(userId)) {
        throw new CustomException(ErrorCode.FORBIDDEN);       // 주최자가 아니면 403
    }
    return meeting;
}
```

> **💡 설계 고민 — 모임 자동 만료(TTL)**
>
> 현재 `expire()`는 방장이 수동 호출해야만 동작한다. 아래 두 가지 방식으로 자동 만료를 고려할 수 있다.
>
> - **방식 A (`expires_at` 컬럼 + 스케줄러)**: `meetings` 테이블에 `expires_at` 추가, Spring `@Scheduled` 배치가 매일 자정에 만료 처리. 추천.
> - **방식 B (지연 만료)**: 모임 조회 시점에 기준일 초과 여부를 체크해 그 자리에서 `expire()` 호출. 스케줄러 불필요.
>
> **권장 만료 기준**: `MAX(candidate_slots.end_time) + 3일` — 후보 슬롯이 모두 지난 시점에서 여유를 두고 자동 만료.  
> 생성일 기준 고정 TTL(예: 14일)보다 자연스럽고, 비회원 게스트 토큰의 사실상 무기한 유효 문제도 함께 해소된다.

# Phase 8 — 내 모임 목록

> **목표 API**: `GET /api/my/meetings?status=&page=&size=`
> Bearer 인증 필요. 내가 만든 모임 목록을 페이징으로 조회한다.

> 🤔 **목록 조회는 왜 `Page`/`Pageable`로 페이징하나요?**
> 모임이 수백 개면 한 번에 다 내려보내는 건 느리고 메모리도 낭비다. `Pageable`(page, size 정보)을 받으면 Spring Data가 DB에서 **해당 페이지만큼만 조회**(내부적으로 페이지네이션 쿼리 사용)하고, `Page<>`는 전체 개수·총 페이지 같은 메타데이터까지 함께 담아 준다. 프론트는 그걸로 "다음 페이지" UI를 만든다.
>
> 🤔 **MyController를 따로 두는 이유는?**
> 이 기능은 `/api/meetings/...`(특정 모임 다루기)와 달리 "**나(로그인한 사용자) 관점의 데이터**"(`/api/my/...`)다. 관점·URL 묶음이 다르므로 컨트롤러를 분리하면 책임이 명확해진다.

```java
public Page<MeetingResponse> findMyMeetings(Long userId, MeetingStatus status, Pageable pageable) {
```

## controller/MyController.java

```java
package com.makeapp.backend.controller;

import com.makeapp.backend.common.ApiResponse;
import com.makeapp.backend.dto.response.MeetingResponse;
import com.makeapp.backend.entity.MeetingStatus;
import com.makeapp.backend.exception.CustomException;
import com.makeapp.backend.exception.ErrorCode;
import com.makeapp.backend.service.MeetingService;
import lombok.RequiredArgsConstructor;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.http.ResponseEntity;
import org.springframework.security.core.Authentication;
import org.springframework.web.bind.annotation.*;

import java.util.Map;

@RestController
@RequestMapping("/api/my")                       // "나" 관점의 API 묶음
@RequiredArgsConstructor
public class MyController {

    private final MeetingService meetingService;

    @GetMapping("/meetings")                     // GET /api/my/meetings?status=&page=&size=
    public ResponseEntity<ApiResponse<Map<String, Object>>> getMyMeetings(
            @RequestParam(required = false) String status,   // 선택: 상태 필터 (없으면 전체)
            @RequestParam(defaultValue = "0") int page,      // 페이지 번호 (0부터)
            @RequestParam(defaultValue = "10") int size,     // 페이지당 개수
            Authentication auth) {
        if (auth == null || !auth.isAuthenticated()) {
            throw new CustomException(ErrorCode.UNAUTHORIZED);
        }
        Long userId = (Long) auth.getPrincipal();
        MeetingStatus meetingStatus = status != null ? MeetingStatus.valueOf(status) : null;  // 문자열 → enum

        Page<MeetingResponse> result = meetingService.findMyMeetings(
                userId, meetingStatus, PageRequest.of(page, size));   // page/size로 Pageable 생성

        // Page 객체에서 내용 + 페이징 정보를 뽑아 응답 Map으로 구성
        return ResponseEntity.ok(ApiResponse.ok(Map.of(
                "content", result.getContent(),           // 현재 페이지의 모임 목록
                "totalElements", result.getTotalElements(),  // 전체 개수
                "totalPages", result.getTotalPages(),     // 전체 페이지 수
                "page", result.getNumber(),               // 현재 페이지 번호
                "size", result.getSize())));              // 페이지 크기
    }
}
```

# 트러블슈팅

## JWT 401 오류가 계속 날 때

- Postman `Authorization` 탭 → `Bearer Token` 타입 선택 후 토큰 입력
- 또는 Headers 탭: Key=`Authorization`, Value=`Bearer eyJhbGci...`
- 토큰 만료(1시간) 시 `POST /api/auth/refresh`로 재발급

## 카카오 인가 코드 `KOE320` 오류

인가 코드 만료 또는 재사용. 브라우저에서 새 코드를 발급받아 즉시 사용.

## Spring Boot 기동 시 `ddl-auto: validate` 오류

Flyway 마이그레이션이 완료되지 않은 상태. `docker-compose ps`로 Oracle `healthy` 확인 후 재기동.

## `@SQLRestriction` 미적용 케이스

`@Query`로 직접 작성한 JPQL/Native Query에는 자동 적용 안 됨.
해당 쿼리에 `AND deleted_at IS NULL` 직접 추가 필요.

## 500 오류 발생 시

IntelliJ 콘솔 스택 트레이스 먼저 확인.
주요 원인: `LazyInitializationException` (트랜잭션 외부에서 지연 로딩), `NullPointerException`.

## React 연동 시 CORS 오류

Phase 1의 `SecurityConfig`에 CORS 설정이 이미 포함되어 있다.  
`allowCredentials(true)`가 없으면 HttpOnly Cookie가 프론트엔드로 전달되지 않으니 반드시 확인할 것.

```java
http.cors(cors -> cors.configurationSource(request -> {
    var config = new org.springframework.web.cors.CorsConfiguration();
    config.setAllowedOrigins(List.of("http://localhost:5173"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
    config.setAllowedHeaders(List.of("*"));
    config.setAllowCredentials(true);   // ← 이 줄이 없으면 쿠키가 안 날아감
    return config;
}));
```
