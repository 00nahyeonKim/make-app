# Make-App 개발 환경 셋업 가이드

> URL 기반 일정 조율 서비스
> 새로 합류하는 팀원이 가장 먼저 읽어야 할 문서

---

## 📋 프로젝트 개요

- **서비스**: URL 기반 일정 조율 (When2Meet 유사)
- **백엔드**: Spring Boot
- **프론트엔드**: React
- **데이터베이스**: Oracle XE 21c (Docker 컨테이너로 구동)
- **스키마 관리**: Flyway (마이그레이션 기반)

이 프로젝트는 **DB만 Docker로 격리**하고 백엔드/프론트엔드는 각자 로컬에서 직접 실행하는 구조입니다. Flyway가 DB 스키마를 git으로 동기화해주므로, 팀원 모두가 동일한 DB 구조를 자동으로 유지합니다.

## 🚀 초기 셋업 (최초 1회만)

### 1. 저장소 클론

```bash
git clone <레포지토리 URL>
cd make-app
```

### 2. 환경 변수 파일 생성

```bash
cp .env.example .env
```

`.env` 파일을 열어서 비밀번호 부분을 채워넣으세요.

```bash
# .env (예시)
ORACLE_SYS_PASSWORD=dev_sys_password
DB_USER=makeapp
DB_PASSWORD=dev_password
```

> ⚠️ `.env` 파일은 git에 올라가지 않습니다 (`.gitignore` 처리). 비밀번호 유출 방지를 위함입니다.

### 3. DB 컨테이너 실행

```bash
docker compose up -d
```

Oracle XE는 **첫 부팅에 1~2분** 정도 걸립니다. 진행 상황 확인:

```bash
docker compose logs -f oracle
```

`DATABASE IS READY TO USE!` 메시지가 보이면 준비 완료입니다.

### 4. 백엔드 실행

```bash
cd backend
./gradlew bootRun
```

첫 실행 시 **Flyway가 자동으로 V1부터 마이그레이션을 적용**합니다. 콘솔에 다음과 같이 나오면 성공:

```
Successfully applied N migrations to schema "MAKEAPP" ...
Tomcat started on port(s): 8080
```

### 5. 프론트엔드 실행 (별도 터미널)

```bash
cd frontend
npm install
npm run dev
```

## 📁 폴더 구조

```
make-app/
├── docker-compose.yml          # DB 컨테이너 정의
├── .env                        # 환경변수 (git ignore)
├── .env.example                # 환경변수 템플릿 (git 포함)
├── .gitignore
├── README.md                   # 이 파일
│
├── db/
│   └── init/                   # 컨테이너 최초 실행 시 1회 동작 SQL
│
├── backend/                    # Spring Boot
│   ├── build.gradle
│   └── src/main/
│       ├── java/
│       └── resources/
│           ├── application.yml
│           └── db/migration/   # ⭐ Flyway 마이그레이션 (스키마 변경 이력)
│
└── frontend/                   # React
    ├── package.json
    └── src/
```

### 핵심 디렉토리 2곳

- **`db/init/`**: 컨테이너가 **처음 만들어질 때 단 한 번** 실행되는 SQL. 사용자 생성, 권한 부여 같은 인프라성 작업 전용. 이미 볼륨이 있으면 스킵됩니다.
- **`backend/src/main/resources/db/migration/`**: Flyway가 관리하는 스키마 변경 이력. **모든 테이블 생성/수정/인덱스 추가는 여기서 합니다.**

두 디렉토리 모두 git으로 관리되므로, 어느 팀원이든 동일한 DB 구조를 얻게 됩니다.

## ⚙️ 핵심 설정 파일

### `docker-compose.yml`

```yaml
services:
  oracle:
    image: gvenzl/oracle-xe:21-slim
    container_name: makeapp-oracle
    ports:
      - "1521:1521"
    environment:
      ORACLE_PASSWORD: ${ORACLE_SYS_PASSWORD}
      APP_USER: ${DB_USER}
      APP_USER_PASSWORD: ${DB_PASSWORD}
    volumes:
      - oracle-data:/opt/oracle/oradata          # 데이터 영속성
      - ./db/init:/container-entrypoint-initdb.d # 초기 SQL
    healthcheck:
      test: ["CMD", "healthcheck.sh"]
      interval: 20s
      timeout: 10s
      retries: 10
      start_period: 90s

volumes:
  oracle-data:
```

**Named Volume `oracle-data`**: DB 데이터 파일을 named volume에 저장하여 컨테이너를 지웠다 다시 만들어도 데이터가 보존됩니다. `docker compose down`은 컨테이너만 삭제하고, `docker compose down -v`까지 가야 데이터가 삭제됩니다.

### `backend/src/main/resources/application.yml`

```yaml
spring:
  application:
    name: make-app

  datasource:
    url: jdbc:oracle:thin:@localhost:1521/XEPDB1
    username: ${DB_USER:makeapp}
    password: ${DB_PASSWORD:dev_password}
    driver-class-name: oracle.jdbc.OracleDriver

  jpa:
    open-in-view: false
    hibernate:
      ddl-auto: validate
    properties:
      hibernate:
        dialect: org.hibernate.dialect.OracleDialect
        format_sql: true

  flyway:
    enabled: true
    baseline-on-migrate: true
    locations: classpath:db/migration

logging:
  level:
    org.hibernate.SQL: DEBUG
    org.hibernate.orm.jdbc.bind: TRACE
```

> ⚠️ **`ddl-auto: validate`는 절대 다른 값으로 바꾸지 마세요.** 자세한 이유는 [반드시 지킬 규칙](#-반드시-지킬-규칙) 섹션 참고.

## 🔄 일상 개발 워크플로우

### 매일 작업 시작 시

```bash
# 1. DB 컨테이너 실행 (꺼져있으면)
docker compose up -d

# 2. 최신 코드 받기
git pull

# 3. 백엔드 실행 → Flyway가 새 마이그레이션 자동 적용
cd backend && ./gradlew bootRun

# 4. 프론트엔드 실행 (별도 터미널)
cd frontend && npm run dev
```

### 작업 종료 시

```bash
# DB 컨테이너만 중지 (데이터는 유지됨)
docker compose down
```

다음 날 `docker compose up -d`만 다시 실행하면 어제 상태 그대로 이어서 작업할 수 있습니다.

## 🗄️ DB 스키마 변경하는 방법

**스키마 변경은 반드시 Flyway 마이그레이션 파일을 통해서만** 합니다.

### 단계별 절차

#### 1. 새 마이그레이션 파일 생성

`backend/src/main/resources/db/migration/` 에 새 파일을 만듭니다.

- 파일명 규칙: **`V{다음번호}__{설명}.sql`**
- 언더스코어 **2개** 주의 (`__`)
- 예: `V3__add_email_column.sql`

#### 2. SQL 작성

```sql
-- V3__add_email_column.sql
ALTER TABLE users ADD email VARCHAR2(100);
```

#### 3. 백엔드 재시작

Flyway가 새 파일을 자동으로 감지하고 실행합니다. 콘솔에 다음과 같이 나옵니다:

```
Migrating schema "MAKEAPP" to version "3 - add email column"
Successfully applied 1 migration
```

#### 4. 엔티티 클래스도 같이 수정

DB 변경 = 엔티티 변경 = 항상 세트입니다.

```java
@Entity
public class User {
    // ...
    private String email;  // 추가
}
```

#### 5. 커밋 & 푸시

```bash
git add backend/src/main/resources/db/migration/V3__add_email_column.sql
git add backend/src/main/java/.../User.java
git commit -m "feat: users 테이블에 email 컬럼 추가"
git push
```

### 팀원이 변경사항을 받으면

```bash
git pull
cd backend && ./gradlew bootRun
```

→ Flyway가 "V3는 아직 실행 안 됐네" 판단 → 자동 적용 → 팀원의 DB도 동일한 구조가 됩니다.

## 🚫 반드시 지킬 규칙

### 1. `ddl-auto: validate` 절대 변경 금지

| 값 | 동작 | 사용 여부 |
|---|---|---|
| `validate` | 엔티티 ↔ DB 스키마 일치 **검증만** | ✅ 사용 |
| `update` | Hibernate가 자동으로 DDL 실행 | ❌ 금지 |
| `create-drop` | 시작/종료 시 테이블 생성/삭제 | ❌ 금지 |
| `create` | 시작 시 테이블 생성 | ❌ 금지 |

`update`를 쓰면 스키마 변경 이력이 안 남고, 두 사람이 같은 테이블을 다르게 수정하면 충돌합니다. **스키마의 진실의 원천은 엔티티 코드가 아니라 마이그레이션 SQL 파일**이어야 합니다.

### 2. 한 번 push된 마이그레이션 파일은 절대 수정 금지

V2를 푸시한 다음 V2 내용을 바꾸면:

- 본인: 이미 V2를 실행한 상태 → 영향 없음
- 팀원: 수정된 V2가 처음으로 실행됨
- 결과: **두 사람의 DB 상태가 달라짐**

추가로, Flyway는 체크섬을 검증하기 때문에 이미 실행된 마이그레이션 파일이 수정되면 **앱 시작 자체를 거부**합니다 (`Migration checksum mismatch` 에러).

**스키마를 수정하고 싶으면 새 마이그레이션 파일(V3, V4 ...)을 추가하세요.** 마이그레이션은 append-only가 원칙입니다.

### 3. 엔티티 클래스만 수정 금지

JPA 엔티티에 컬럼을 추가해놓고 마이그레이션 파일을 안 만들면, `ddl-auto: validate`가 시작 시점에 에러를 띄웁니다.

**엔티티 수정 ↔ 마이그레이션 파일 작성**, 항상 같이 다닙니다.

### 4. 진짜 테이블 생성은 `db/init/` 에서 하지 않기

`db/init/` 디렉토리는 **컨테이너 최초 셋업용**입니다. 권한 부여, 테이블스페이스 생성 같은 인프라성 SQL만 넣습니다. 일반 테이블 생성은 반드시 Flyway 마이그레이션 파일로 하세요.

## 🧰 자주 쓰는 명령어

### Docker

```bash
# 컨테이너 시작
docker compose up -d

# 컨테이너 중지 (데이터 유지)

```

```bash
# 실행
./gradlew bootRun

./gradlew build

# 테스트 실행
./gradlew test

# 깨끗이 다시 빌드
./gradlew clean build
```

## 🔧 트러블슈팅

### Oracle 컨테이너가 안 뜸

- Docker Desktop이 실행 중인지 확인
- 1521 포트가 이미 사용 중이지 않은지 확인 (`lsof -i :1521` 또는 `netstat -ano | findstr 1521`)
- 첫 부팅은 1~2분 소요. `docker compose logs -f oracle`로 진행 상황 확인

### 백엔드 시작 시 `Schema-validation: missing table` 에러

엔티티에는 있는 테이블/컬럼이 DB에는 없을 때 발생.

→ 해당 변경에 대한 마이그레이션 파일이 누락됐는지 확인. 새 마이그레이션 파일을 추가하면 해결.

### 백엔드 시작 시 `Validation failed for query for method ...`

엔티티의 필드 타입이나 이름이 DB와 불일치.

→ 엔티티 클래스와 마이그레이션 파일을 비교해서 차이점을 찾고 맞춰주세요.

### Flyway 에러: `Migration checksum mismatch`

이미 실행된 마이그레이션 파일의 내용이 변경됐을 때 발생.

**해결책:**

- **운영 환경**: 절대 안 됩니다. 반드시 새 마이그레이션 파일(V+1)로 변경.
- **개발 단계**: DB 완전 초기화 후 다시 시작.
  ```bash
  docker compose down -v
  docker compose up -d
  ./gradlew bootRun
  ```

### Flyway 에러: `Migration failed`

마이그레이션 SQL 자체에 문법 오류 또는 제약 조건 위반.

→ 에러 메시지의 SQL 문장을 확인하고 수정. 이미 부분적으로 실행됐다면 DB 초기화가 필요할 수 있습니다.

### DB를 완전히 초기화하고 싶을 때

```bash
docker compose down -v   # 볼륨까지 삭제
docker compose up -d     # 빈 DB로 다시 시작
cd backend && ./gradlew bootRun  # V1부터 다시 적용됨
```

> ⚠️ 이 작업은 **현재 DB의 모든 데이터를 영구 삭제**합니다. 신중하게 실행하세요.
