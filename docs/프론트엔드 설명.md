# Make-App 프런트엔드 프로젝트 개요 및 구조 설계 지침

> 이 문서는 Make-App 프런트엔드 개발 시 AI 에이전트에게 제공할 프로젝트 컨텍스트 문서이다.  
> AI는 이 문서를 기준으로 서비스 목적, 기술 스택, 폴더 구조, 라우팅, 상태 관리, API 연동 방향을 이해하고 코드를 작성한다.

---

## 1. 서비스 개요

### 1.1 서비스명

Make-App

### 1.2 서비스 한 줄 설명

Make-App은 초대 URL을 통해 지인들이 가능한 시간을 선택하고, 리더가 최적의 약속 시간을 확정할 수 있도록 돕는 URL 기반 일정 조율 서비스이다.

### 1.3 서비스 목적

사용자는 복잡한 회원가입 절차 없이 초대 링크를 공유하여 여러 사람의 가능한 시간을 수집하고, 참여자들의 응답을 바탕으로 가장 적절한 약속 시간을 확인할 수 있다.

서비스는 다음 흐름을 중심으로 동작한다.

1. 리더가 소셜로그인 후 모임을 생성한다.
2. 리더가 후보 날짜와 후보 시간을 등록한다.
3. 서비스가 초대 URL과 결과 공유 URL을 생성한다.
4. 팔로워는 공유받은 URL로 접속한다.
5. 팔로워는 소셜로그인 또는 비회원 방식으로 참여한다.
6. 팔로워는 자신이 가능한 시간을 선택한다.
7. 결과 화면에서 시간대별 가능 인원과 추천 결과를 확인한다.
8. 리더는 최종 일정을 확정하거나 결과 URL을 공유한다.

## 2. 주요 사용자 역할

### 2.1 공통 사용자

메인 화면에 접속하고 서비스 소개를 확인하며, 일정 만들기 또는 공유받은 초대 URL로 진입할 수 있는 사용자이다.

### 2.2 리더

모임을 생성하고 초대 URL을 공유하는 사용자이다. 리더는 반드시 소셜로그인을 해야 하며, 로그인한 사용자의 `userId`를 기준으로 모임 소유자 권한을 가진다.

리더가 할 수 있는 일은 다음과 같다.

- 소셜로그인
- 모임 생성
- 모임명 입력
- 예상 참여 인원 입력 또는 생략
- 후보 날짜와 시간 선택
- 초대 URL 복사 및 공유
- 결과 확인
- 최종 일정 확정
- 자신이 만든 모임 조회

### 2.3 팔로워

리더가 공유한 초대 URL로 접속하여 자신의 가능 시간을 등록하는 사용자이다. 팔로워는 소셜로그인 또는 비회원 방식으로 참여할 수 있다.

팔로워가 할 수 있는 일은 다음과 같다.

- 초대 URL 접속
- 모임 정보 확인
- 소셜로그인 참여
- 비회원 이름 또는 닉네임 입력
- 가능한 시간 선택
- 본인 응답 수정
- 참여 현황 및 결과 확인

### 2.4 비회원 팔로워

소셜로그인을 하지 않고 이름 또는 닉네임을 입력하여 참여하는 사용자이다. 비회원 팔로워는 서버에서 발급한 `guestToken`으로 식별한다.

프런트엔드는 비회원 참여 후 발급받은 `guestToken`을 브라우저 저장소에 저장하여 같은 브라우저에서 재접속했을 때 기존 응답을 불러올 수 있도록 처리한다.

## 4. 구조 설계 기본 방향

이번 프로젝트는 규모가 큰 편이 아니므로 `features/` 기반의 도메인 중심 구조는 사용하지 않는다.

대신 파일의 성격과 역할이 비슷한 것끼리 모으는 단순한 구조를 사용한다.

예를 들면 다음과 같다.

- API 요청 함수는 `api/`
- 재사용 UI 컴포넌트는 `components/`
- 화면 페이지는 `pages/`
- 라우터 설정은 `routes/`
- 전역 상태는 `stores/`
- 재사용 Hook은 `hooks/`
- 순수 유틸 함수는 `utils/`
- 공통 타입은 `types/`

이 구조의 목적은 다음과 같다.

- 처음 보는 팀원도 파일 위치를 쉽게 찾을 수 있게 한다.
- 기능 단위 폴더가 너무 많아져서 구조가 복잡해지는 것을 방지한다.
- 작은 프로젝트에 맞게 단순하고 빠르게 개발할 수 있도록 한다.
- 추후 프로젝트가 커지면 필요한 부분만 점진적으로 분리할 수 있게 한다.

## 6. 디렉터리별 책임

### 6.1 `api/`

백엔드 API 요청 함수를 모아두는 디렉터리이다.

API 호출 로직은 페이지 컴포넌트에 직접 작성하지 않는다. 페이지에서는 `api/`에 정의된 함수를 호출한다.

파일 예시는 다음과 같다.

```txt
api/
  httpClient.ts
  authApi.ts
  meetingApi.ts
  participantApi.ts
  availabilityApi.ts
  resultApi.ts
  myApi.ts
```

각 파일의 책임은 다음과 같다.

| 파일 | 책임 |
| --- | --- |
| `httpClient.ts` | Base URL, JSON 처리, 공통 헤더, 에러 처리 |
| `authApi.ts` | 카카오 로그인 콜백, 로그아웃, 토큰 재발급 |
| `meetingApi.ts` | 모임 생성, 초대 URL 조회, 결과 URL 조회, 모임 수정, 확정, 마감, 삭제 |
| `participantApi.ts` | 참여자 등록, 참여자 목록 조회, 본인 참여 정보 조회, 응답 완료 처리 |
| `availabilityApi.ts` | 가능 시간 등록 및 수정, 응답 현황 조회 |
| `resultApi.ts` | 결과 화면 데이터 조회 |
| `myApi.ts` | 내가 만든 모임 목록 조회 |

### 6.2 `components/`

프로젝트 전체에서 재사용 가능한 공통 UI 컴포넌트를 둔다.

예시:

- Button
- Input
- Textarea
- Select
- Modal
- Card
- Badge
- LoadingSpinner
- ErrorMessage
- EmptyState

공통 컴포넌트는 특정 API, 특정 store, 특정 페이지 흐름에 직접 의존하지 않도록 작성한다.

좋은 예시는 다음과 같다.

```tsx
<Button>일정 만들기</Button>
<Input label="모임명" />
<LoadingSpinner />
<ErrorMessage message="모임 정보를 불러오지 못했습니다." />
```

좋지 않은 예시는 다음과 같다.

```tsx
<Button onClick={createMeeting}>모임 생성</Button>
```

공통 컴포넌트 내부에서 직접 API를 호출하지 않는다.

### 6.3 `pages/`

라우트에 직접 연결되는 실제 화면 컴포넌트를 둔다.

페이지 컴포넌트는 다음 역할을 한다.

- URL 파라미터 읽기
- API 함수 호출
- 상태 관리
- 공통 컴포넌트 조합
- 화면 전체 레이아웃 구성

이번 프로젝트는 `features/`를 사용하지 않으므로, 특정 화면에서만 사용하는 작은 UI 조각은 처음에는 해당 페이지 파일 안에 작성해도 된다.

다만 페이지 파일이 너무 길어지면 `components/`로 분리한다.

기준은 다음과 같다.

```txt
한 페이지에서만 쓰고 코드가 짧다 → 페이지 내부에 작성
여러 페이지에서 재사용된다 → components/로 분리
페이지 코드가 너무 길어진다 → components/로 분리
```

### 6.4 `routes/`
React Router 설정을 관리한다.

포함될 수 있는 파일은 다음과 같다.

```txt
routes/
  router.tsx
  ProtectedRoute.tsx
  GuestOrMemberRoute.tsx
```


각 파일의 책임은 다음과 같다.

| 파일 | 책임 |
| --- | --- |
| `router.tsx` | 전체 라우트 정의 |
| `ProtectedRoute.tsx` | 로그인 사용자만 접근 가능한 라우트 처리 |
| `GuestOrMemberRoute.tsx` | 소셜 사용자 또는 게스트 토큰이 있는 사용자만 접근 가능한 라우트 처리 |

### 6.5 `stores/`

Zustand 전역 상태를 관리한다.

앱 전체에서 공유되는 상태를 `stores/`에 모아 관리한다.

권장 파일은 다음과 같다.

```txt
stores/
  authStore.ts
  guestStore.ts
  meetingDraftStore.ts
```

각 파일의 책임은 다음과 같다.

| 파일 | 책임 |
| --- | --- |
| `authStore.ts` | 로그인 여부, accessToken, refreshToken, 사용자 정보 |
| `guestStore.ts` | 비회원 guestToken, displayName, 참여자 정보 |
| `meetingDraftStore.ts` | 모임 생성 중 임시 입력값, 후보 날짜와 시간 |

서버에서 매번 조회할 수 있는 데이터까지 무조건 Zustand에 저장하지 않는다.

Zustand는 다음 상태를 우선 관리한다.

- 로그인 정보
- 토큰 정보
- 게스트 식별 정보
- 여러 화면에서 이어지는 임시 입력값
- UI 전역 상태

### 6.6 `hooks/`

여러 화면에서 재사용 가능한 React Hook을 둔다.

예시:

```txt
hooks/
  useAuth.ts
  useCopyToClipboard.ts
  useGuestToken.ts
```

Hook은 화면 로직을 줄이고 재사용성을 높이기 위해 사용한다.

예를 들면 다음과 같다.

- 로그인 여부 확인
- 게스트 토큰 조회
- 클립보드 복사
- 모달 열림 상태 관리

### 6.7 `utils/`

React에 의존하지 않는 순수 유틸리티 함수를 둔다.

예시:

```txt
utils/
  dateFormat.ts
  timeFormat.ts
  tokenStorage.ts
  validators.ts
  urlBuilder.ts
```

유틸 함수는 가능하면 입력값과 반환값이 명확한 순수 함수로 작성한다.

예시:

```ts
formatDate("2026-06-01")
validateMeetingName(name)
buildInviteUrl(inviteToken)
```

### 6.8 `types/`

공통 타입과 API 응답 타입을 둔다.

`types/` 디렉터리에 성격별 타입 파일을 둔다.

예시:

```txt
types/
  api.ts
  auth.ts
  meeting.ts
  participant.ts
  availability.ts
  result.ts
```

## 8. API 연동 설계 지침

### 8.1 공통 API 클라이언트

API 호출은 `api/httpClient.ts`에서 공통 처리한다.

공통 처리 대상은 다음과 같다.

- 개발 서버 Base URL 설정
- 운영 서버 Base URL 설정
- JSON 요청 처리
- JSON 응답 처리
- `Authorization: Bearer {accessToken}` 헤더 설정
- `X-Guest-Token: {guestToken}` 헤더 설정
- 공통 에러 응답 처리

### 8.2 API 함수 작성 위치

API 함수는 모두 `api/` 디렉터리에 작성한다.

예시:

```txt
api/authApi.ts
api/meetingApi.ts
api/participantApi.ts
api/availabilityApi.ts
api/resultApi.ts
api/myApi.ts
```

페이지 컴포넌트에서는 다음처럼 호출한다.

```ts
import { createMeeting } from "../api/meetingApi";

const response = await createMeeting(request);
```

### 8.3 API 응답 형식

백엔드 API는 기본적으로 다음 응답 래퍼를 사용한다.

```ts
export type ApiResponse<T> = {
  success: boolean;
  data: T;
};
```

에러 응답은 다음 형태를 기준으로 처리한다.

```ts
export type ApiErrorResponse = {
  success: false;
  error: {
    code: string;
    message: string;
  };
};
```

## 9. 인증 및 토큰 관리 지침

### 9.1 소셜로그인 사용자

카카오 로그인 성공 후 백엔드에서 발급받은 JWT Access Token을 사용한다.

프런트엔드는 다음 정보를 저장하고 활용한다.

- `accessToken`
- `refreshToken`
- 로그인 사용자 `id`
- 로그인 사용자 `name`

### 9.2 비회원 사용자

비회원 참여자는 서버에서 발급한 `guestToken`으로 식별한다.

프런트엔드는 다음 정보를 저장하고 활용한다.

- `guestToken`
- `displayName`
- 참여 중인 `inviteToken`
- 참여자 `id`

### 9.3 저장소 사용 기준

초기 개발 단계에서는 `localStorage`를 사용할 수 있다.

권장 key 예시는 다음과 같다.

```ts
export const STORAGE_KEYS = {
  ACCESS_TOKEN: "make_app_access_token",
  REFRESH_TOKEN: "make_app_refresh_token",
  USER: "make_app_user",
  GUEST_TOKEN_PREFIX: "make_app_guest_token_",
};
```

게스트 토큰은 모임별로 다를 수 있으므로 `inviteToken`을 조합해서 저장한다.

```ts
const guestTokenKey = `${STORAGE_KEYS.GUEST_TOKEN_PREFIX}${inviteToken}`;
```

## 10. Tailwind CSS 사용 지침

Tailwind CSS는 공통 레이아웃, 버튼, 카드, 폼, 반응형 화면을 빠르게 구성하기 위해 사용한다.

기본 원칙은 다음과 같다.

- 가능한 한 별도 CSS 파일보다 Tailwind 유틸리티 클래스를 우선 사용한다.
- 반복되는 스타일은 공통 컴포넌트로 분리한다.
- 복잡한 조건부 스타일은 문자열 조합 함수 또는 유틸 함수를 사용할 수 있다.
- 모바일 환경을 우선 고려하고, 필요한 경우 `sm:`, `md:`, `lg:` 반응형 클래스를 사용한다.
- `index.css`에는 Tailwind 설정과 전역 스타일만 둔다.

## 11. React Router 사용 지침

React Router는 메인, 로그인, 모임 생성, 초대 URL, 응답 입력, 결과 화면, 마이페이지 등의 화면 이동을 관리한다.

기본 원칙은 다음과 같다.

- 라우팅 설정은 `routes/` 디렉터리에서 관리한다.
- `pages/`에는 실제 화면 컴포넌트만 둔다.
- 인증이 필요한 라우트는 보호 라우트로 분리한다.
- URL 토큰 기반 화면은 동적 라우트 파라미터를 사용한다.
- 없는 경로는 `NotFoundPage`로 처리한다.

## 12. Zustand 사용 지침

Zustand는 로그인 정보, 토큰, 사용자 정보, 비회원 토큰, 모임 생성 중 임시 상태처럼 여러 화면에서 공유해야 하는 상태를 관리한다.

기본 원칙은 다음과 같다.

- 이번 프로젝트에서는 `stores/`에 전역 상태를 모아 관리한다.
- 단일 페이지 안에서만 쓰는 값은 `useState`를 우선 사용한다.
- 앱 전체에서 필요한 인증 정보와 토큰은 Zustand store를 사용한다.
- 서버 데이터 캐싱 용도로 Zustand를 과도하게 사용하지 않는다.

## 15. AI 코드 작성 지침

AI가 코드를 작성할 때는 다음 규칙을 따른다.

### 15.1 구조 우선 원칙

기능을 구현하기 전에 해당 코드가 어느 디렉터리에 위치해야 하는지 먼저 판단한다.

- API 호출이면 `api/`
- 재사용 UI이면 `components/`
- 실제 화면이면 `pages/`
- 라우터 설정이면 `routes/`
- 전역 상태이면 `stores/`
- 재사용 Hook이면 `hooks/`
- 순수 유틸 함수이면 `utils/`
- 타입이면 `types/`


### 15.2 컴포넌트 작성 원칙

- 한 컴포넌트가 너무 많은 책임을 갖지 않도록 분리한다.
- 페이지 컴포넌트는 전체 화면 흐름을 담당한다.
- 공통 UI는 `components/`로 분리한다.
- props 타입을 명확히 작성한다.
- 서버 응답 타입과 화면 상태 타입을 구분한다.
- Tailwind CSS를 우선 사용한다.

### 15.3 상태 관리 원칙

- 단일 페이지 안에서만 쓰는 값은 `useState`를 사용한다.
- 여러 페이지에서 공유해야 하는 값은 Zustand store를 사용한다.
- 인증 정보와 토큰은 `authStore.ts`에서 관리한다.
- 게스트 토큰과 비회원 참여 정보는 `guestStore.ts`에서 관리한다.
- 모임 생성 중 임시 입력값은 필요할 경우 `meetingDraftStore.ts`에서 관리한다.

### 15.4 API 연동 원칙

- API 호출 로직은 페이지 컴포넌트에 직접 작성하지 않는다.
- 공통 fetch 로직은 `api/httpClient.ts`에 둔다.
- API 그룹별 함수는 `api/*Api.ts`에서 작성한다.
- API 요청과 응답 타입은 명확히 정의한다.
- 인증이 필요한 요청은 accessToken 또는 guestToken을 적절히 포함한다.

### 15.5 라우팅 원칙

- 라우트 정의는 `routes/router.tsx` 에서 관리한다.
- 로그인 필수 라우트는 `ProtectedRoute`로 감싼다.
- 게스트 또는 로그인 참여자만 접근 가능한 화면은 별도 보호 라우트를 둔다.
- 존재하지 않는 경로는 `NotFoundPage`로 처리한다.

## 17. 현재 구조에서 App.tsx 사용 여부

현재 `main.tsx`에서 `RouterProvider`를 직접 렌더링하는 구조라면 `App.tsx`는 필수 파일이 아니다.

현재 구조 예시는 다음과 같다.

```tsx
createRoot(document.getElementById("root")!).render(
  <RouterProvider router={router} />,
);
```

이 경우 실행 흐름은 다음과 같다.

```txt
main.tsx
  → RouterProvider
    → routes/router.tsx 또는 router/router.tsx
      → BasicLayout
        → pages
```

따라서 `App.tsx`는 없어도 된다.

다만 추후 전역 Provider가 많아지면 `App.tsx`를 다시 사용할 수 있다.

예시:

```tsx
function App() {
  return (
    <QueryClientProvider client={queryClient}>
      <RouterProvider router={router} />
    </QueryClientProvider>
  );
}
```

현재 단계에서는 `main.tsx`에서 라우터를 직접 연결하는 방식으로 진행해도 충분하다.

## 18. 최종 설계 방향 요약

Make-App 프런트엔드는 다음 방향으로 설계한다.

- 서비스는 URL 기반 일정 조율 흐름을 중심으로 구성한다.
- 리더는 소셜로그인을 통해 모임을 생성하고 관리한다.
- 팔로워는 소셜로그인 또는 비회원 방식으로 참여한다.
- 비회원은 `guestToken`으로 식별한다.
- 프로젝트 규모를 고려하여 `features/` 구조는 사용하지 않는다.
- 파일 성격별 구조를 사용한다.
- API 함수는 `api/`에 둔다.
- 공통 UI는 `components/`에 둔다.
- 페이지 컴포넌트는 `pages/`에 둔다.
- 라우팅은 `routes/` 에서 관리한다.
- 재사용 Hook은 `hooks/`에 둔다.
- 순수 유틸 함수는 `utils/`에 둔다.
- 공통 타입은 `types/`에 둔다.
- 전역 상태는 `stores/`에 둔다.
- 스타일링은 Tailwind CSS를 우선 사용한다.
- 라우팅은 React Router를 사용한다.
- 상태 관리는 Zustand를 사용한다.
- AI가 코드를 작성할 때는 단순한 구조와 명확한 책임 분리를 우선한다.
